01

How to use this handbook

This is the page to read if you inherit OpenFlyover and have to keep it alive alone: understand how it was made, find your way in the code, change a setting, fix a failing test, publish a release. It does not repeat what other documents of the repository already say well: it points to them.

If you know the web already

Skip the explanations of part 3 and go to the repository tour, the domains and the recipes.

If you come from classic software

Read in order. Part 3 is the dictionary: each web notion is compared to something you know (a build tool, a state machine, a thread, a database) and then shown in this repository.

If something is broken now

Jump to day-to-day (commands, reading a failing test, debugging) and to the pitfalls list in its last section.

02

Genesis and history

OpenFlyover makes a 3D flyover film from a GPX or FIT track recorded on an outing (hike, run, ride, ski tour). The track is laid on real terrain covered with aerial photos; a virtual camera flies along it; the person edits the film on a timeline and exports a video, a still image or a printable poster. Everything runs on the user's machine: no account, no API key, no paid service, no application server.

The history in this repository runs from 5 to 20 October 2026: 648 commits when this page was last verified (608 at version 2.2.0). The first commit already contains the whole skeleton (geo maths, import, terrain engine, scene, store, sample track); everything else grew on it in the phases below. A mental model for a developer new to the web

This part translates the web vocabulary into what you already know, then shows each notion in this repository. Read the analogies as a first approximation: where one misleads, the text says so.

The browser is the runtime, the web page is the program

A desktop program is compiled for an operating system and calls its libraries. A web application is delivered as files (JavaScript, CSS, images) that a browser downloads and runs. The browser provides everything the program needs: a UI toolkit (HTML and CSS), 2D and 3D drawing, audio, video encoding, networking, local storage, file saving. OpenFlyover uses a large share of that platform: 3D (WebGL), 2D canvas, video encoding (WebCodecs), audio mixing, Cache Storage, a service worker.

Analogy The browser is a virtual machine with a very large standard library and a GUI toolkit built in. The « executable » is a folder of text files; « installing » is downloading them. The user's machine is the server of everything the app does.

In this repository. index.html is the only page: an empty <div id="root"> and a script tag for /src/main.tsx. src/main.tsx installs a few global services (appearance, language, offline tiles, export guard, service worker) and mounts the React tree. The desktop application is the same page shown in the web view of the operating system by Tauri.

HTML, CSS, JavaScript, TypeScript

HTML

The tree of elements the browser displays (the DOM). Here it is almost empty: React builds the elements from code.

Here index.html, plus an inline script that sets the theme before the first paint to avoid a flash.

CSS

Rules that give elements their look and layout. Think of it as a declarative styling language with inheritance and a cascade (later and more specific rules win).

Here src/ui/theme.css (tokens), utilities.css, primitives/*.css; see the UI layer.

JavaScript

The language of the page: dynamically typed, single-threaded, event-driven, with async/await on top of promises (futures). The browser runs one main thread that handles input, drawing and your code in turns.

Here a few .mjs tools (scripts/, e2e/run.mjs) and src/platform/serviceWorker.js; everything else is TypeScript.

TypeScript

JavaScript plus static types, checked by a compiler before the program runs and erased afterwards: no type exists at run time. Closest to a gradually typed language with a structural type system (two types are compatible when their shapes match).

Here every file of src/ is .ts, or .tsx when it contains JSX (HTML-like notation used by React).

The TypeScript settings that shape how you write code are in tsconfig.app.json:

SettingWhat it means for you

npm, package.json, Vite: the build chain

Node.js and npm

Node runs JavaScript outside a browser: here only for development tools (build, tests, scripts), never at run time. npm is the package manager: package.json is the manifest, package-lock.json the lock file with exact versions and hashes, node_modules/ the local install (ignored by git). Like Maven or Cargo.

Here npm ci installs exactly the lock file (use it, not npm install, unless you mean to change dependencies). "type": "module" makes .js/.mjs files ES modules. "private": true prevents an accidental publish.

Vite (build tool and dev server)

In development it serves your source modules to the browser one by one and reloads the changed one (hot module replacement): no build step to wait for. For production it bundles hundreds of modules into a few optimised files, splitting rarely needed code into separate chunks loaded on demand. Vite 8 bundles with Rolldown (note the rolldownOptions key in the config).

Here vite.config.ts: plugins react(), tailwindcss() and two local ones (below); base from BASE_PATH (GitHub Pages serves under /openflyover/, pages.yml sets it); test block for Vitest.

Code splitting and import()

A dynamic import('./X') is an on-demand load: the bundler emits a separate file, fetched when the line runs. It is how a 3 MB library stays out of the first screen. Comparable to lazy-loading a plugin DLL.

Here React.lazy(() => import(...)) for the 3D scene (src/ui/Stage.tsx), the export drawer and the offline panel (src/App.tsx), the atmosphere (FlyoverCanvas.tsx); import('mediabunny') in export/encoder.ts; the FIT reader in import/index.ts. See ARCHITECTURE.md « Loading ».

React: components, props, state, hooks, effects

React builds a user interface from components: functions that receive inputs (props) and return a description of what to show (JSX). You never edit the screen yourself. You change state, React calls your component functions again, compares the new description with the old one, and updates only what differs.

Analogy An immediate-mode UI with a diff engine: the screen is a pure function of the state, re-evaluated on change. The model-view-controller of classic desktop code is still there, only spread differently (table below).

State

Data a component remembers between calls (useState), or data shared by many components (a store). Changing it schedules a new render. It must be changed by replacing values (new object, new array), never by mutating them: React and the store detect change by reference.

Hooks

Functions whose name starts with use that give a component memory and lifecycle: useState, useMemo (cache a computed value), useRef (a mutable box that does not trigger a render), useEffect (run code after the screen updated, with cleanup). Rule: call hooks unconditionally, at the top level of a component; oxlint enforces it (react/rules-of-hooks is an error in .oxlintrc.json).

Effects

useEffect(fn, deps) runs fn after render and again when a dependency changes; its return value is the cleanup. It is where a component talks to the outside (subscribe, fetch, create a GPU resource). Think of it as a constructor/destructor pair tied to some inputs. In development StrictMode runs it twice on purpose to catch leaks: TerrainLayer.tsx says why it creates the terrain engine in the effect and disposes it in the cleanup.

lazy() declares a component loaded on first use; <Suspense fallback=...> shows a placeholder meanwhile. Used for the 3D scene, the export drawer and the atmosphere.

State management: one store, selectors, pure modules

The app state lives in a zustand store, a small library: create() returns a hook (useAppStore) that holds an object and its actions. A component calls it with a selector ((s) => s.settings.exposureEv) and is re-rendered only when that selected value changes. Outside React the same store is read with useAppStore.getState() and watched with useAppStore.subscribe(...).

Analogy A single in-memory, observable application model with typed commands (actions) and queries (selectors). Subscribing with a selector is like a SQL view over it; a change notification fires only when the view's result changed.
  • The main store is useAppStore in src/state/store.ts: tracks, derived bounds and frameOrigin, settings (one Settings object holding every user setting, with the film inside it), playback (progress, film time, speed), project name, selection.
  • Settings are replaced, not edited: setSetting(key, value) does set({ settings: { ...get().settings, [key]: value } }). That new object is what undo (src/project/history.ts, which compares snapshots) and the « Modifié » marker (isProjectDirty in src/ui/shell.ts, by reference) rely on.
  • Twenty other small stores hold what is not a project setting: export progress (export/store.ts), weather, landmarks, water, region, offline packs, media table, music preview, toasts, preferences, project library… Each is a create() in its own module.
  • Pure modules do the computing: geo/, import/, terrain/, flyover/, most of film/, overlay/, weather/, poster/layout.ts take values and return values (no React, no store, no DOM; the headers say « Pure functions »). They are the easy part to test and the part the export reuses.

Three.js, react-three-fiber, WebGL, the render loop

GPU and WebGL

The GPU is a massively parallel processor that draws triangles. WebGL is the browser's API to give it work (an OpenGL ES profile). You upload geometry and textures, and write small programs called shaders that run per vertex and per pixel. Comparable to a compute device with its own memory and its own language.

Three.js

A library that hides most of WebGL behind a scene graph: a tree of objects (groups, meshes, lights, a camera). You change object positions; the library renders the tree. The unit of drawing is a frame: one image.

react-three-fiber (R3F)

Lets React components describe that scene tree: a component returns three.js objects, and hooks give access to the renderer. useFrame(cb) registers a callback run on every frame (the render loop). Here three.js is 0.186 and fiber 9.

The render loop

A game loop: input, update, draw, about 60 times a second. R3F can run it continuously or on demand (frameloop="demand"): it draws only when something asks. OpenFlyover is on demand (below) to save power when nothing moves.

In this repository. The 3D view is <Canvas> in src/scene/FlyoverCanvas.tsx:

<Canvas gl={gl} camera={CAMERA} dpr={[1, BUDGET.maxPixelRatio]} frameloop="demand" flat shadows="percentage" ...>
  {hasTracks && (
    <TerrainLayer>
      <RenderOnDemand />
      <TrackLines />
      <WaterLayer />
      <FlyoverRig />
      <CameraRig />
      <Labels />
      {atmosphere && (<Suspense fallback={null}><AtmosphereLayer /></Suspense>)}
      <ExportController drawOverlay={overlayDrawer.draw} />
    </TerrainLayer>
  )}
</Canvas>
  • TerrainLayer creates the terrain engine (src/terrain/engine.ts, no React) and shares it with its children through a context (useTerrainContext). Children are layers: the track, water, labels, the rig that moves the camera and marker, the atmosphere (sky, clouds, post-processing) and the export controller. The scene is mounted only once there is a track (hasTracks).
  • On-demand rendering. src/scene/renderOnDemand.ts asks for frames while the film plays, tiles load or the camera fits, and for WAKE_FRAMES = 30 frames after any change of the stores the scene reads (wakeScene()). The time step is capped (MAX_FRAME_DELTA_S = 0.25 s) so playback does not jump after a pause. During an export the loop is switched off (frameloop 'never') and ExportController draws each frame itself.
  • FlyoverRig is the heart: on each frame it reads progress and film time from the store, computes the camera view with a pure function (computeFilmView, reached through filmViewAt in scene/filmView.ts) and places camera and marker.
  • The Canvas needs a GPU. Without one (CI, e2e) Chromium falls back to a software renderer (SwiftShader): correct but slow, so the e2e run uses long timeouts.

Canvas 2D and OffscreenCanvas

A <canvas> is a bitmap you draw on with commands (lines, text, images), like a software GDI or Cairo surface. OffscreenCanvas is the same without being on screen. Here the film overlay (titles, counters, profile, mini-map, credits) is painted by the single function drawOverlay(ctx, frame, settings, size, assets, extras) in src/overlay/draw.ts. The preview calls it on a transparent canvas laid over the 3D view (OverlayCanvas.tsx, redrawn on the next animation frame after a store change); the export calls it on an OffscreenCanvas for every frame (composeFrame in src/export/capture.ts). The poster uses the same approach (src/poster/draw.ts). All sizes derive from the frame size (1 unit = 1 % of the shorter side), so any resolution works.

Web Workers: none, on purpose or by default

A Web Worker is a background thread with no access to the page, communicating by messages. This project starts none (no new Worker anywhere in src/). Heavy work runs on the main thread, and two mechanisms keep the page responsive: the browser itself decodes images off-thread (createImageBitmap in terrain/fetch.ts) and the export yields to the event loop once per frame (yieldToEventLoop in export/capture.ts). If you ever need a worker, Vite supports new Worker(new URL('./w.ts', import.meta.url), { type: 'module' }); nothing here prepares for it. The only worker-like thing is the service worker.

WebCodecs, mediabunny and the audio pipeline

WebCodecs is a browser API to the system's video and audio encoders (VideoEncoder), fast and often hardware-backed. It produces compressed frames, not files. mediabunny (an npm library, MPL-2.0) writes them into an MP4 or WebM container, like a muxer in ffmpeg. Here src/export/encoder.ts picks the first codec the machine can encode (CODEC_CANDIDATES: H.264 in MP4, HEVC in MP4, VP9 in WebM, VP8 in WebM; AV1 in MP4 is offered only where the device can encode it and is used only when the user picks it, so that « Automatique » never lands on a slow software encoder), streams the file to disk when the platform allows, and loads mediabunny lazily. Sound is mixed by film/audio.ts with an OfflineAudioContext over the exact film length, so the mix is deterministic, never real time; on request it is then brought to a chosen loudness (film/loudness.ts, export pipeline). Where the web view has no WebCodecs (Linux desktop), export/nativeEncoder.ts sends raw frames to the system ffmpeg through Rust (next part).

Tailwind utilities

Instead of writing a CSS rule per component, you put small single-purpose classes on the element (flex, gap-2, text-hint, rounded-sm). The Rust and Tauri part

The website is enough for most people. The desktop application exists for what a web page cannot do well: write a very long film straight to disk, open a .opnflvr project with a double-click, encode video on Linux where the web view has none, render a folder of tracks from a terminal, read the machine's memory and CPU load. It is a thin native shell around the same built site.

Tauri in plain terms

Tauri

A framework that opens a native window containing a web view (the operating system's own browser engine: Edge WebView2 on Windows, WebKit on macOS, WebKitGTK on Linux) and loads your site into it. A small Rust program runs next to it. Comparable to Electron, but with the system's engine instead of a bundled Chromium and Rust instead of Node as the native side.

Here Tauri 2 (src-tauri/Cargo.toml, @tauri-apps/cli and @tauri-apps/api in package.json).

Rust, crate, Cargo

Rust is a compiled language with ownership-based memory safety (no garbage collector, no null: Option<T>; errors are values: Result<T, E> and the ? operator). A crate is a package (library or program). Cargo is its build tool and package manager: Cargo.toml is the manifest, Cargo.lock pins versions (committed: about 520 locked crates), cargo build, cargo test, target/ is the build output (git-ignored). Like Maven and its repository, with the lock file always kept.

Tauri command and IPC

A Rust function marked #[tauri::command] that the page can call by name through invoke('name', args), which crosses from the web view to the Rust process (inter-process communication) and returns a promise. It is an RPC; arguments and results are JSON, or raw bytes for a binary body.

Here ten commands, listed below.

Plugins, capabilities, CSP

Plugins add ready-made native features (dialogs, files, opening a URL). Capabilities are an allow-list: a window may call only the commands and plugin functions granted to it, with file scopes. The CSP (content security policy) tells the web view which origins the page may load scripts from or connect to. Together they play the role of a sandbox policy.

Here src-tauri/capabilities/default.json and the security.csp block of tauri.conf.json.

Security model, in one paragraph

The page may read and write only: files picked in a dialog (the dialog plugin adds each path to the fs scope), the two command-line folders (added by cli.rs), project files opened by the system (added by opened.rs), and $APPDATA/tiles and $APPDATA/projects. Of the opener plugin it may only open https links and show a file in its folder. video.rs refuses to write a file that is not in the scope. The CSP restricts script to 'self' and lists every tile, weather, Overpass and Strava host the page may contact: a new data source must be added to img-src and/or connect-src there, or the desktop app silently blocks it while the website works.

The data flow, from a GPX file to an exported film

  1. Open a file. « Ouvrir », a drop on the window, « Essayer avec l'exemple », or a Strava activity. openFiles in src/ui/projectActions.ts splits projects from tracks (routeOpenedFiles), then importTrackFiles → runImport builds one job per file.
  2. Parse. importFile (src/import/index.ts) picks parseGpx or, after a lazy import('./fit'), parseFit; buildTrack (import/stats.ts) computes statistics (distance, gain, duration, bounds); assignColors gives each track a colour. One failing file never stops the others (runImportJobs).
  3. Complete and store. importFiles (src/ui/importFlow.ts) fills missing elevations from the terrain source (completeImportedElevations) and calls useAppStore.addTracks, which recomputes bounds, fixes frameOrigin once (computeFrameOrigin), picks the regional imagery (IGN or swisstopo when the tracks lie inside their coverage: pickRegionalImagery) and bumps fitRequest.
  4. Build the scene. With a track present, FlyoverCanvas mounts TerrainLayer, which creates the terrain engine for the local frame; CameraRig fits the camera to the tracks on fitRequest. Each frame the engine selects tiles by screen-space error, fetches and decodes them, and builds meshes (terrain).
  5. Compute the film. useFilmClock() (src/scene/usePacing.ts) turns the track, the film, the flight duration, the pacing and the landmarks into a FilmClock (filmClockFor in src/film/clock.ts): a pure mapping from film time to phase (opening, flight, stop, closing) and progress. New films get automatic stops (film/assemble.ts).
  6. Play. FlyoverRig advances playback (setProgress(progress, timeS)), calls filmViewAt (which calls computeFilmView) and places the camera and the marker; OverlayCanvas redraws the overlay.
  7. Fetch side data. The panels call syncWeather (weather/store.ts) and syncLandmarks (osm/store.ts) from effects; the results are published in small stores that the sky, clouds, labels and overlay read. (This is why the side panels stay mounted: App.tsx notes their side effects.)
  8. Export. ExportPanel calls useExportStore.getState().start(request); ExportController (mounted in the canvas) runs runExport: frame schedule, then for each frame set progress and film time, renderSettledFrame (render until the visible tiles are final), composeFrame (WebGL image plus overlay into an OffscreenCanvas), session.addFrame; finally session.finish() and the file is closed.
  9. Save. serializeProject → encodeProjectFile (gzip with a signature) → getPlatform().saveDocument.

Import and geography

What. Turns a GPX or FIT file (or a Strava activity, or a planned route) into a Track, and converts between geographic, Earth-centred, local and tile coordinates. Key idea. A track is plain data, built once; everything downstream (path, camera, overlay, weather) derives from it and caches per track object.

  • GPX (import/gpx.ts, parseGpx): the browser's DOMParser, matching elements on localName so any extension vocabulary (Garmin, Cluetrust) works. A time without a time zone is read as UTC (a review fix).
  • FIT (import/fit.ts, parseFit): an in-house binary decoder written from the public FIT description; reads record, hr, session, sport and activity messages; positions are semicircles converted to degrees. Loaded only when the first .fit arrives (dynamic import).
  • Statistics (import/stats.ts): distance, bounds, duration; ascent and descent from smoothed elevations with a hysteresis threshold so GPS jitter does not count as climbing.
  • Missing elevation: terrain/elevation.ts reads heights from the terrain tiles (automatically at import for usual outings, otherwise « Calculer l'altitude »); Track.elevationEstimated remembers it.
  • Corrected figures (« Corriger les chiffres », Track.statsOverride): distance, D+, highest point, duration and top speed typed by hand. They are only figures for the cards (prepareOverlayTrack) and the poster (correctedStats); Track.stats stays what the points say, so the camera, profile and counters are unchanged.
  • Planned outing (plan/timing.ts): a route without times gets estimated ones from a date, a start time, an activity and a pace, so the sun, counters and weather work.
  • Strava (strava/): the user brings their own Strava application; client id and secret are kept in the platform storage and sent only to strava.com. Pure URL builders and parsers are tested; the rest calls fetch.
  • Chaining (import/chain.ts): several tracks merged into one route; after chaining, items placed on the old tracks are not moved (a known limit in how-it-works.html).
  • Geo (geo/): createLocalFrame, lonLatToEcef, tile maths (tilesForBounds, tileBounds, parentOf, childrenOf), geoid undulation (geoidUndulation, a 1° EGM96 grid generated into egm96Grid.ts by scripts/gen-geoid.mjs; edit the script, not the generated file).
Where to look src/import/, src/geo/, src/ui/importFlow.ts, src/ui/projectActions.ts. Tests: src/import/*.test.ts with fixtures in src/import/__fixtures__/ (a real Garmin run is read in a test), src/geo/*.test.ts. Design: Modules, Track chaining, Strava import.
How to modify To read a new file type, write parseX(...): Track[] that ends with buildTrack, add its extension to supportedExtension and the switch in importFile (import/index.ts), add it to the dialog filters in ui/projectActions.ts (chooseTracksToImport, chooseFilesToOpen), add a fixture and tests, and add the new Track['source'] value in core/types.ts if it is a new origin.

Terrain and imagery: fetch, cache, level of detail

What. Builds the 3D ground from open tiles: elevation tiles become a height grid, aerial photos become a texture, and a quadtree decides which tiles to show at which detail. Key idea. A tile is replaced by its four children only when its triangles would look bigger than about 3 pixels on screen (errorTargetPx); the parent stays until the children are ready, so the ground never flashes empty.

  • Sources (terrain/sources.ts): TERRAIN_SOURCES (Mapterhorn by default, AWS Terrain Tiles) and IMAGERY_SOURCES (ids: ign-ortho, swisstopo, arcgis-world-imagery, the hand-picked national photos basemap-at, gsi-photo and usgs-imagery, and the maps ign-plan, swisstopo-carte, opentopomap; terrain: mapterhorn, aws-terrarium). An id that was removed is mapped to a replacement in REMOVED_IMAGERY_SOURCES (project/document.ts). Every value was checked by hand; the log is docs/sources.md. This file is the single source of truth: buildTileUrl(source, key) builds URLs, sourceCovers tests coverage. The default imagery is Esri World Imagery; addTracks switches to IGN or swisstopo when the tracks fall inside their coverage, until the user picks one by hand. « Date des photos » (terrain/imageryDates.ts, setting imageryDate) swaps the IGN layer for a year of flight, or Esri for a release of its Wayback archive; datedImagerySource gives the engine a source with its own id and, for IGN, the latest photos as fallback where the year is blank.
  • Fetch (terrain/fetch.ts, createTileFetcher): fetch() then createImageBitmap(), a priority queue, 12 concurrent requests, de-duplication of requests in flight, an LRU cache of bitmaps (size from deviceBudget()), retries with growing delays (250 ms, ×4), abort support. Offline packs are read before the network through setStoredTileReader.
  • Heights (dem.ts): Terrarium encoding h = R*256 + G + B/256 − 32768; a pixel with alpha 0 or the all-zero sentinel is « no data ». heightField.ts answers sampleHeight(lon, lat) from the deepest loaded tile; the engine's own sampleHeight reads the tile actually drawn there, which is what the track draping and camera use.
  • Mesh (mesh.ts): a grid of 64 segments per tile edge (65 × 65 vertices) in the local frame, plus skirts (edges lowered) that hide cracks between detail levels.
  • Imagery (imagery.ts): for a terrain tile at zoom z the imagery sub-tiles at z + imageryZoomOffset are drawn into one canvas texture; the canvas is released once the GPU has it (phones cannot afford the memory) and redrawn after a WebGL context loss.
  • Engine (quadtree.ts decides what to draw and load; engine.ts owns loading, unloading, retries and the Three.js group). Dependencies are injected (EngineDeps) so tests run without network or GPU. In an export, setExporting(true) makes the engine retry failed tiles and report pendingVisibleTiles so the export can wait for a complete image.
  • Phones: core/deviceBudget.ts lowers caches, texture size and pixel ratio on touch devices; the level of detail holds a tile cap there (lodFactor).
Where to look src/terrain/, src/scene/TerrainLayer.tsx, terrainContext.ts, terrainLayerSetup.ts, src/core/deviceBudget.ts, vite.config.ts (TILE_PROXIES). Tests: src/terrain/*.test.ts (engine with fake downloads), src/scene/TerrainLayer.test.tsx. Design: Terrain engine, Device budget.
How to modify A new tile source: recipe. A different level-of-detail trade-off: errorTargetPx in the engine options and EngineTuning in engine.ts; re-measure on a phone, because the phone tile cap is tuned (the history has several fixes for white or flipping tiles).

Flyover camera and pacing

What. Decides where the camera is and where it looks, at every instant. Key idea. The view is a pure function of progress, film time, camera settings and a terrain height sampler: computeCameraView keeps no memory between frames, so the export can compute any frame on its own and the preview always matches it.

  • Path (flyover/path.ts): a track flattened into a polyline indexed by cumulative distance; samplePath(path, distanceM) maps progress to a position at constant ground speed. trackPathOf caches per track; smooth.ts averages GPS jitter (smoothedTrackPath), and the marker, camera and drawn line all use the same smoothed positions.
  • Camera (camera.ts, cameraSettings.ts): six styles (CAMERA_STYLES: chase, sway, orbit, top, cinematic, free; free follows nothing but the keyframes, each fixed at its own place on the track: freeView in filmCamera.ts), twelve presets (CAMERA_PRESETS), a minimum ground clearance, and a sight-line check against the relief. Time-based motions (orbit, cinematic swing) follow the film time so they keep moving while the progress is held. timeSmoothing.ts smooths in film time.
  • Film camera (filmCamera.ts, computeFilmView): wraps the flight camera with the opening and closing shots (SHOT_STYLES: aucune, descente, saut, situation, balayage), the camera of a stop (orbit, wide, fixed), camera keys, and the region view. Over a steep mountain the shots take a lift (shotLift, liftedBlend): the extra height that the glide slope, the ground and the line of sight ask for is read at 40 fixed points of the shot and spread over the neighbouring ones, so a ridge under the line of sight becomes a gentle hump instead of a jerk of the camera (a function of the shot only, so it follows the rule of no memory between frames). With several tracks, follow.ts says what the camera follows.
  • Audit (filmAudit.ts: replayFilm, auditPoses, auditFilmCamera): replays a film frame by frame (30 a second) and lists, with their time, the jolts of the camera (a jolt is a sudden change of speed: above AUDIT_JOLT_LIMIT = 0.025, where a calm flight stays under 0.006), a camera too close to the ground and a marker out of the frame. It is how a camera bug is looked for and how it is kept from coming back: a bug found on a real project becomes a case of its test. It is not in the interface: it is run from a test (how, in Debugging).
  • Pacing (pacing.ts): only the film-time to progress mapping changes (raised-cosine slow-downs, pauses, speed portions); progress stays the fraction of distance. flightPacing(...) returns totalTime, progressAtTime, timeAtProgress. The default flight lasts 60 s, adjustable 15 to 600 s in 1 s steps. flightSpeed.ts turns that duration into the marker's average speed (« × temps réel », km/h) and back, so « Régler par » in ui/FlightDurationField.tsx can set either: only flyoverDurationS is stored.
  • Sun, climbs, colours: sun.ts (the sun date under the marker: a dawn outing replays its sunrise; and the sun of the opening and closing shots: « Accéléré » is a time lapse of shotSunHoursOf(shot) hours, 4 by default and 1 to 12 shot by shot through FilmShot.sunHours, added to the sun date by shotSunDate), climbs.ts (detected climbs, categories 4 to HC), trackColor.ts (colour by speed, slope, elevation, heart rate…, with viridis and magma scales), nights.ts (multi-day tracks: each night is a pause of the film clock, with a dusk, a night and a dawn), and film/days.ts (the days of such a track and their figures: the card of each day, film.dayCards, is drawn from them at every frame like a stage card by dayCardAt and dayWidget, and « Vue haute pendant la nuit » is dayViewAt in filmCamera.ts: during the pause before a day the camera rises to look at that day's route from above, then dives back to the marker at dawn).
  • Several tracks: sequence.ts (« À la suite »: stages flown one after the other on a never-stored sequence track), race.ts (« En parallèle »: ghost race and leaderboard).
Where to look src/flyover/, src/scene/FlyoverRig.tsx (applies the view), src/scene/filmView.ts. Tests: src/flyover/*.test.ts including continuity checks (__fixtures__/smoothness.ts) and filmAudit.test.ts, which replays the opening and closing of the 12 presets with 4 shot styles on 3 invented terrains at 30 frames a second and fails on a jolt of the camera, a camera too close to the ground or a marker out of the frame (see « Audit of the film camera » in ARCHITECTURE.md). Design: Flyover.
How to modify New camera style: add it to CAMERA_STYLES and CAMERA_STYLE_LABELS in cameraSettings.ts (i18n key camera.style.<id> in the camera.ts of each language), handle it where camera.ts switches on the style, make it a function of film time only, add it to the continuity test. The film and the timeline

What. The edited film: what is added on top of the flight along the first track, in the project's words « la base, c'est le GPX ». Key idea. settings.film is plain data; one pure mapping, the film clock, says what the film shows at a film time; the timeline UI only turns gestures into pure edits.

  • Model (film/model.ts): Film holds opening and closing shots, stops, speeds (speed portions), cameraKeys, paramKeys (speed, exposure, sun hour, grading, 3D-label opacity), markerKeys, texts, media, audio, pois, nights, dayCards (the cards of the days of a long track), junctions and stage durations for « À la suite ». Ids are stable (stop-3, text-1, auto-4520 for a generated stop). DEFAULT_FILM, isValidFilm, withFilmDefaults make it saveable.
  • Clock (film/clock.ts): [0, opening) overview shot; the flight with pacing, speed portions and stops; the closing shot. clock.stateAt(timeS) returns a FilmState (phase: opening, flight, stop, closing; progress; flightTimeS; the current stop). Preview and export both use it. For a track recorded over several days, each night is a pause of this clock (dusk, night and dawn last the seconds of film.nights) and clock.days lists the days with the time of their card and whether the camera takes its high view.
  • Automatic assembly (film/assemble.ts): when a track loads, stops are generated at highlights (new films: 'temps-forts'; films saved before the timeline: 'rythme'). Editing a stop first writes the generated ones out (materializeStops).
  • Edits (film/timeline.ts and friends): time/pixel scale, snapping, add, remove, drag, attach a text to a stop. All pure. The component calls editFilm(edit, { stops, step }) (scene/usePacing.ts), which materialises stops, lets attached items follow moved stops and slowed or sped-up sections (followStops: texts and media are re-timed with routeTime so they keep their place on the route, the music stays put), and commits one undo step through getSettingsHistory().transaction.
  • Working with blocks (film/timeline.ts, ui/Timeline.tsx, ui/blockClipboard.ts): Ctrl + click picks several texts, photos, videos or music clips, one drag moves them all (dragBlocks) and Delete removes them in one undo step. Ctrl+C and Ctrl+V copy them to the app's own clipboard (not the system one, so a text selected on the page still copies as before) and paste them with their gaps, the earliest at the playhead (copyBlocks, pasteBlocks). Ripple means that what follows moves up to close the gap: Shift+Delete, or Shift held while an end is dragged, shifts the later blocks of the same lane by the same amount (rippleRemove, rippleDrag). Stops, speed sections and keys are not copied or rippled: they sit at a place of the route (in metres), and moving one shifts the whole clock.
  • Work area, lanes, zoom, filmstrip: I and O set an in and an out point (film/workArea.ts: markIn, markOut, loopTime); a band on the ruler shows them and the preview loops inside them (FlyoverRig), Shift+X clears them. The work area is not saved, not an undo step, and the export still renders the whole film. Each row of the timeline, a lane, can be folded to a thin strip and locked so that its blocks no longer move (ui/laneState.ts); both are remembered on the device in localStorage (openflyover.lanes.v1), not in the project. Z zooms the timeline to the selected block, else to the work area, else to the whole film (zoomToSpan); « Réglages › Timeline » shows the time in frames and chooses what the magnet snaps to. A video block that is wide enough shows a filmstrip, a few small frames of the clip behind its name (ui/Filmstrip.tsx, read once per clip with mediabunny, never saved).
  • Keyboard: the list shown in the help dialog (« ? ») is SHORTCUTS in ui/shortcuts.ts. The keys that act on the film (K play and pause, J and L one frame, I, O and Shift+X, S, T, Delete, Shift+Delete, Ctrl+D, X, Ctrl+C, Ctrl+V, Alt+arrows) are handled in one place, the SeekShortcuts component of App.tsx, which reads the film clock without re-rendering the shell.
  • Opening title and closing card (film/cards.ts): they are blocks of the « Textes » lane, but their data stays in the overlay settings (overlay.title, overlay.end). Dragging the block, or either edge, can place the card anywhere in the film: it writes title.window or end.window (CardWindow: a start and an end in film seconds; the « Apparition » slider no longer exists) and the card fades in and out inside it. A card that was never placed keeps the window of earlier versions, so old projects play as before. Delete switches the card off and keeps its settings. The inspector is shared (ui/FilmInspector.tsx): the card block (card-title, card-end) and the shot block (opening, closing) open the same panel, the card in a first group and the camera shot under « Plan de caméra ». What each card shows besides its title is CardExtras (overlay/settings.ts: figures, line, image, showProfile, showMinimap, all optional so old projects need no migration); titleWidget and endWidget draw them with cardStats and cardGraphics (draw.ts), the picture comes decoded from createCardImages (overlay/assets.ts).
  • Automatic film (film/autoFilm.ts, ui/autoFilm.ts, ui/AutoFilmDialog.tsx): « Film automatique » is the first section of the « Survol » tab. It opens a dialog with three gabarits (templates): « Reel 30 s », « Résumé 1 min » and « Souvenir 3 min ».   • Keys: camera keys (flyover/cameraKeys.ts), parameter keys (film/paramKeys.ts; FILM_PARAMS lists the keyable settings: speed, exposure, sun hour, saturation, contrast, warmth, vignette and the opacity of the 3D labels) and marker keys (film/markerKeys.ts) pin values along the track.   • Media and music (film/media.ts, video.ts, audio.ts, beats.ts, exif.ts): the media table maps an id to a downscaled picture or to the original clip or sound bytes, so settings and undo hold only ids while the project stays one self-contained file. Music has volume envelopes (fades, ducking) shared by preview and export, and beat detection for snapping.

Overlay and widgets

What. Everything drawn over the 3D image: opening and closing cards, counters, elevation profile, mini-map, weather, logo, free text, ghost-race leaderboard, timeline texts and photos, credits. Key idea. It is not web page elements: one synchronous function paints a 2D canvas (drawOverlay), called by the preview and by the export, so the film shows what the preview shows.

  • Settings (overlay/settings.ts): OverlaySettings (enabled, style, title and end (the opening title and the closing card, each with an optional window in film seconds), counters, profile, logo, text, weather, minimap, leaderboard, credits, optional overrides and labelColors), DEFAULT_OVERLAY, isValidOverlay, withOverlayDefaults. A widget has an anchor on a 3 × 3 grid (OVERLAY_ANCHORS), a size, and optionally a free offset in pixels.
  • Styles (themes.ts, structures.ts): seven styles (OVERLAY_STYLES); some (Cinéma, Journal de bord, Tableau sportif) have a structure of their own, not just other colours. A style's layout is applied when it is chosen (withStyleLayout).
  • Data (data.ts): prepareOverlayTrack does per-track work once; overlayFrameAt(data, progress) is a cheap pure function. The cards of the days of a long track are not texts: dayCardAt reads the film time and the figures of each day at every frame and dayWidget (draw.ts) draws them, like the card of a stage « À la suite », so they follow the track, the nights and the weather. The opening title and the closing card fade in and out inside their window (titleCardOpacityOf, endCardOpacityOf).
  • Drawing (draw.ts): everything derives from the frame size (1 u = 1 % of the shorter side). Fonts and the logo are loaded beforehand (assets.ts) because drawing is synchronous.
  • Not in the film: what is HTML over the 3D view is absent from the export, for example the « Zones de sécurité » guides and the panels. To appear in the film, an element must be a widget drawn here.
  • Bridge (exportOverlay.ts): createOverlayDrawer for the export, with media frames decoded before each frame is composed.

Weather and OpenStreetMap data

  • Weather (weather/openMeteo.ts): a few places sampled along the track, the hourly values of its days fetched in one request to the Open-Meteo archive (past outing) or forecast (up to 16 days ahead, FORECAST_DAYS), cached per place and UTC day (archive days in memory and storage, forecast for 3 hours). A refusal (HTTP 429) becomes a message that names the quota used up, minute, hour or day (tooManyMessage); the later stages of « À la suite » are fetched one at a time (syncStageWeather), and a failed one is reported in the weather panel with a « Réessayer » button. series.ts is the data model with interpolation in time and place; sceneWeather.ts turns it into scene parameters (dimmed sun, haze, veiled sky, exposure) and sceneClouds.ts into cloud layers (the cloud cover is read at up to 12 places, about one every 10 km, so the sky changes along the track; the clouds also cast shadows on the terrain, setting cloudShadows, scene/cloudShaders.ts). Both are pure functions of (data, instant, place, setting), so the export renders the same weather for the same frame. weather/store.ts holds the result; syncWeather is idempotent so effects may call it freely.
  • Snow (« Neige », new in 4.0): the day's snow depth, snowfall and temperature already come with the weather request (snow_depth is one more hourly variable, no extra request). weather/snowLine.ts is a small pure model: for the UTC day under the marker, at each station (blended by distance, one day giving way to the next around midnight so the line never jumps), no snow on the ground and none falling means no snow; otherwise the snow line is the altitude where the mean temperature reaches 0 °C (6.5 °C per 1000 m from the station's elevation), and when at least 2 cm lie on the ground the line cannot be above the station. The constants (lapse rate, 2 cm and 20 cm thresholds, the 150 m and 300 m transition bands) are at the top of the file. The drawing is in terrain/snowShader.ts: createMaterial in terrain/engine.ts extends each tile's material with a few lines of shader (the same technique as the water), which turn the colour of the ground white above the line, so the sun, the shadows and the grading light the snow like anything else. The ragged limit is a noise computed from the position (no image), steep slopes keep the rock, and the look is tuned in the fragmentSnow string (noise sizes, slope thresholds, snow colour). scene/SnowLayer.tsx hands the line to the shader on every frame from the settings, the track under the marker and the weather store: it depends only on the film progress, so the export shows what the preview shows. The setting is settings.snow (meteo, manuelle, aucune); its panel is SnowControl in ui/SettingsPanel.tsx. Tests: weather/snowLine.test.ts (the rule), terrain/snowShader.test.ts (the patch still fits three's shader after an upgrade).
  • Landmarks (osm/overpass.ts): one bounded Overpass query per track (a plain bounding box is far cheaper than around: on a polyline), one request at a time, one retry then the next endpoint, form-encoded POST so the browser sends a « simple » CORS request, cached for 30 days (CACHE_TTL_MS). Distance to the track is computed locally in landmarks.ts, so changing the kinds or the distance never sends a new request. Each landmark is « Auto », « Toujours » or « Jamais » shown (landmarkMode, withMode); the density (few, normal, many) caps the Auto ones; « Garder les Toujours » dismisses the others until « Relancer la recherche » (dismissedIds); ui/LandmarkMap.tsx is the window with the map and the elevation profile to pick them. osm/water.ts (lakes and rivers for the water layer) and osm/region.ts (the administrative region highlighted by the « situation » shot) use the same client.
  • Water (osm/water.ts, osm/coast.ts, scene/WaterLayer.tsx): one switch, « Eau reflétante (mer, lacs et rivières) » (settings.water), draws three kinds of water from two cached Overpass requests per track. The first (waterQuery) gives the lakes and river areas as polygons. The second (waterLinesQuery) gives the coastline and the rivers, canals and streams that OpenStreetMap maps only as lines. The sea is the tricky one: a coastline is a line with the land on its left, so coast.ts cuts the track corridor into rectangles, clips the coast to each, and closes the water on the right of the coast along the rectangle’s edge (seaPolygons; an island becomes a hole). A rectangle that cannot be closed becomes a flat plane, and nothing is drawn when no coast is near. The sea is flat at 0 m; SEA_LIFT_M in WaterLayer.tsx raises it a little so that a beach is not flooded. A line river is turned into a ribbon by scene/riverStrip.ts; its width is the width tag, else the value of its type in LINE_WIDTH_M (osm/water.ts: river 12 m, canal 8 m, stream 2.5 m). Everything is drawn by the same material and one merged geometry, draped on the relief again when tiles arrive. The size caps are constants too: MAX_COAST_POINTS, MAX_LINE_LENGTH_M, WATER_LINE_MARGIN_M.
  • Glaciers (no setting of their own: they follow « Neige », drawn unless it is « Aucune », new in 4.1). The snow follows the weather of the day, so in summer a glacier would show only the photo; osm/glacier.ts asks OpenStreetMap (same Overpass client and cache) for the natural=glacier polygons within 5 km of the track and keeps the large ones (at least 2 hectares, at most 200). scene/glacierMesh.ts cuts them with the same grid of squares as the water, so the mesh has points inside the glacier and follows the relief, and scene/GlacierLayer.tsx puts that mesh on the ground like the water (and works out the slope under each point so the sun shades the ice). The look is in scene/glacierMaterial.ts: it reuses the snow's white and its noise from terrain/snowShader.ts and adds the crevasses (thin dark lines of the noise along the flow), a little more blue in the shade, a lower opacity on the very steep faces and a soft edge. To change the look, edit the fragmentGlacier string (opacity GLACIER_OPACITY, STEEP_OPACITY, the darkness of the crevasses, the 140 m patches); to change what is kept, the constants at the top of osm/glacier.ts. Tests: osm/glacier.test.ts, scene/glacierMesh.test.ts (the mesh, and the shader patch still fitting three's shader).
  • Forests (the « Forêts » setting, drawn as 3D trees). Four small files, from the data to the screen. osm/forest.ts asks OpenStreetMap (same Overpass client and cache as the landmarks) for the forests around the track and keeps them as simple polygons. scene/forestPoints.ts decides where the trees stand: a regular grid of cells, one tree in each, placed by a « hash » (a small calculation that always gives the same number for the same cell), so the trees never move between two runs and the exported film shows the same trees as the preview. It also cuts the forests into squares of 1.5 km (« chunks ») and stops when the device's budget is reached (maxTrees in core/deviceBudget.ts: 250,000 on a computer, 60,000 on a phone), starting with the squares nearest to the track. scene/treeGeometry.ts holds the two tree shapes (a conifer and a broadleaf, about thirty triangles each). scene/ForestLayer.tsx puts them on the relief like the water and the track: only the squares within 6 km of the camera are drawn and put on the ground, and the trees shrink to nothing over the last 500 m so none pops in.
  • Privacy and terms: services receive only the tile area, a few points rounded to 1 km for the weather, and the box around the track for landmarks; Open-Meteo is for non-commercial use, Esri tiles follow Esri’s terms (README.md « Data sources »).
Where to look src/weather/, src/osm/, src/ui/WeatherPanel.tsx, src/ui/LandmarkPanel.tsx, src/scene/Labels.tsx, WaterLayer.tsx, ForestLayer.tsx, CloudsLayer.tsx. Tests: src/weather/*.test.ts, src/osm/*.test.ts (network mocked). Design: Historical weather, OpenStreetMap landmarks, Weather in the scene.

The export pipeline

What. Produces an MP4 or WebM video (16:9, 9:16, 1:1, 4:5, 21:9, 720p to 4K, 24, 30 or 60 fps), a PNG or JPEG still, a folder of numbered PNG images (one per frame), the overlay alone on a transparent background, several formats in one go, one film per track of a folder, and the poster. Key idea. The export never plays in real time: it walks a list of frames, and each frame waits until its terrain is final, so a slow computer gives the same film, only later.

  1. ExportPanel builds an ExportRequest and calls useExportStore.getState().start(request) (phase starting). The destination file is chosen from the click that starts it (chooseVideoDestination), so the website's file picker still has the user gesture.
  2. ExportController, mounted inside the canvas, sees the request and runs runExport: buildFrameSchedule gives the progress of each frame, buildFrameTimes its film time (one extra second held at the start, two at the end). Playback is paused, frameloop is set to 'never', the renderer is resized to the video size at pixel ratio 1.
  3. For each frame: filmClock.stateAt(time); the motion-blur sub-frames (shutterSamples); renderSettledFrame renders until the engine reports no pending visible tile (up to 5 minutes per frame, then the export stops with the tile named: tileFailureMessage); composeFrame draws the WebGL canvas and the overlay into an OffscreenCanvas.
  4. session.addFrame(i) hands the frame to the encoder (createVideoEncoder: WebCodecs through mediabunny; or createNativeVideoEncoder: Rust and ffmpeg). Encoding overlaps the render of the next frame. Held frames (stops, holds) reuse the previous image when nothing moves with time.
  5. session.finish() closes the file (streamed to disk when the platform allows, else built in memory and downloaded). Everything is restored on success, error or cancel. State goes rendering → finalizing → done | error | canceled in export/store.ts; ended renders are kept in a history (history.ts, historyStore.ts).
  • Quality tiers (qualityTier.ts): « Standard / Haute / Maximale » set the bitrate (QUALITY_BITS_PER_PIXEL in encoder.ts, a codec factor, a device cap) and how much the costly effects are computed at export time only; the project is never rewritten.
  • Formats for platforms (PLATFORM_PRESETS in schedule.ts, the chips above « Format »): one click sets the proportions, the size, the frame rate, H.264 and a bitrate chosen by hand for YouTube 4K or HD, Reels / TikTok / Shorts, Instagram / Facebook and square (withPlatformPreset, one undo step); the chip stays lit while the settings still match it exactly (platformPresetOf). A phone or tablet still caps the size.
  • File name and place: video.nameTemplate is a template such as {project} – {format} with six words ({project}, {track}, {format}, {resolution}, {fps}, {date}; expandNameTemplate); empty means the track's name, and batches keep their own names. In Chrome and Edge the website's save dialog reopens where the last one was; the desktop one opens on the folder of the last film (openflyover.lastFilmFolder) and, once the film is written, « Ouvrir le dossier » shows the file in the system's file manager (Platform.revealFile; a web page cannot do that).
  • Time before the first film (history.ts: rateFromHistory, estimateRenderSeconds): the summary shows « ≈ … de rendu ». The speed (time per frame and per megapixel) comes from the films rendered in this session or, if there is none yet, from the last film in the export history that ran to the end. A first film is slower because its tiles are not loaded yet, so this is an estimate.
  • Loudness (film/loudness.ts; « Normaliser le volume » under « Encodage › Volume », off by default): just before the encoder gets the mixed soundtrack, ExportController calls normaliseLoudness. It measures how loud the sound is in LUFS (the standard unit of perceived loudness, ITU-R BS.1770), raises or lowers it to −14, −16 or −23 LUFS (at most +15 dB up), then a limiter keeps the peaks under −1 dB so that nothing clips. Pure functions, tested on a sine wave of known loudness. The preview is not normalised.
  • AV1 and image sequence: AV1 (MP4) is offered only where the device can encode it and « Automatique » never picks it. « Séquence d'images PNG » (sequenceEncoder.ts, ExportRequest.sequence) writes name_00001.png, name_00002.png… into a folder chosen on the click, for an editing application: no sound, no extra seconds held at the start and the end, and a cancel keeps the images already written. It plays the part of a video session so that runExport does not change (VideoEncodeSession.codec is a SessionCodec, container and codec as plain strings, so that « png / png » fits). ProRes is not offered: WebCodecs cannot encode it (mediabunny can only write it), and the desktop route would be the system's ffmpeg with a new choice in the native encoder; nobody has built that.
  • Batch (batch.ts, trackFilms.ts): « Plusieurs formats » and « Un film par trace » run jobs one after another through the same store. cliRender.ts does the same from the desktop command line.
  • Render queue (queue.ts, src/ui/RenderQueue.tsx): « File de rendus », a section of « Plusieurs formats », renders several projects one after the other. An item is the exact text of serializeProject taken when the project was added (so a later edit changes nothing), its name, the formats ticked, whether its still image and its poster are queued, and a status. Waiting items can be moved up or down (moveItem). runQueue (pure) picks the next waiting item and marks failures; runRenderQueue keeps the open project, holds the batch store « running » (so the app is as busy as during a batch: no autosave, no edit), shows each snapshot with parseProject + applyProject like « Ouvrir », renders its films with runBatch + exportJob from batch.ts, and puts the open project back. The queue lives in the platform storage like the render history (parseQueue never throws); a run cut short comes back as « en attente » and restarts from the first image. Snapshots over about 1 MB are not kept after closing (the item then shows as failed), and the output folder is never stored on the web (a handle cannot be): it is asked again. The desktop app remembers the path of the last folder (chooseQueueFolder, key openflyover.renderQueue.folder) and asks again only if it is gone or out of the fs scope. When the page is hidden, wait uses the timer of a tiny Web Worker instead of spinning through message ports.
  • Rendering in the background (wait in capture.ts): a hidden page (a hidden tab, a minimised window) gets its timers once a second, and the export waited for tiles with a 16 ms timer, so it crawled. wait now checks document.visibilityState: shown, a timer; hidden, a loop of MessageChannel turns (not throttled) until the deadline. The frames themselves never needed the page to be visible. A page the system puts to sleep (a phone, a laptop lid) still stops: that cannot be fixed from the code.
  • Phone safety (guard.ts): screen kept on, a flag in sessionStorage to report an export the browser killed, breadcrumbs of the steps; diagnostic.ts builds a report kept in French on purpose (withLanguage('fr', …)) because it is pasted into bug reports.
  • Poster (src/poster/): a pure layout (layout.ts: boxes in pixels from the size, style and rows present; text fitting) and a drawing function (draw.ts), fed by export.ts with a 3D still.
Where to look src/export/ (start with ExportController.tsx and capture.ts), src/ui/ExportPanel.tsx, src/film/loudness.ts, src/poster/, src-tauri/src/video.rs. Tests: src/export/*.test.ts (encoder and network faked; sequenceEncoder.test.ts, history.test.ts), src/film/loudness.test.ts, e2e scenarios « export » and « historique » (render a real 320 × 180 film). Design: Video export, Export quality tiers, Poster.
How to modify Recipe: add an export format. Do not make a frame depend on the previous one. When you add something that moves with time, make the export loop aware that it is « timed » (sceneMovesWithTime and the timed test in runExport), or held frames will not redraw it.

Project persistence and migration

What. One self-contained file holding every setting, the tracks and the media. Key idea. Settings are handled generically over the keys of DEFAULT_SETTINGS: a new setting is saved, validated and restored without editing the persistence code.

  • Document (project/document.ts): PROJECT_FORMAT = 'openflyover-project', PROJECT_VERSION = 2; serializeProject(state, name, media) writes tracks column by column (lon, lat, ele, time…, with a fixed number of decimals) and settings as they are; parseProject(text) returns a LoadedProject with warnings.
  • Validation: sanitizeSettings(raw, base) takes each key of DEFAULT_SETTINGS from the file when it has the same shape as the default (sameShape) and passes its extra check in SETTING_CHECKS (enums, catalogue ids, ranges); otherwise the default is used and the key is listed as invalid (a warning, never a failure). SETTING_UPGRADES fills in fields added since a project was saved (withCameraDefaults, withOverlayDefaults…), so old files and presets keep loading.
  • Migrations: MIGRATIONS[n] upgrades a document from version n to n + 1; migrateProject runs the chain and refuses a newer version. Today there is one migration (1 to 2).
  • File container (project/file.ts): .opnflvr is an 8-byte header (the ASCII signature OPNFLVR and a version byte: 1 gzip, 2 plain) followed by the JSON text, gzip-compressed with the browser's CompressionStream. Older .json projects have no signature and are read as they are.
  • Apply (project/apply.ts): applyProject replaces tracks, settings, media and playback speed, then fits the camera. Opening is refused during an export.
  • Undo (project/history.ts): createHistory watches immutable settings snapshots, keeps for each step only the keys that changed, merges changes to the same keys within 400 ms (COALESCE_MS, a slider drag) and keeps 100 steps. transaction(fn) groups several changes (a preset); beginGesture keeps one step open.
  • Presets (project/presets.ts): named sets of settings in the key openflyover.presets.v1, by scope (PRESET_SCOPES: tout, carte, trace, habillage, prise-de-vue).
  • « Mes projets » (platform/projectLibrary.ts): projects kept inside the app (Cache Storage on the web, files on the desktop), saved automatically (installLibraryAutosave in ui/library.ts).
Where to look src/project/, src/ui/projectActions.ts, src/ui/library.ts, src/platform/projectLibrary.ts. Tests: src/project/*.test.ts (including legacy.test.ts), e2e scenario « projet » (save and reopen in a fresh page). Design: Project.
How to modify A new setting: recipe. A change of shape of an existing setting (rename a field, split an object): write a SETTING_UPGRADES entry so old files still load, and keep the old shape in a test (legacy.test.ts). Only a change that cannot be expressed that way raises PROJECT_VERSION with a MIGRATIONS entry; add a fixture of the old version.

Internationalisation

What. The interface and the texts drawn into films and posters exist in five languages: French (the reference and default), English, Spanish, Italian and German. Key idea. French defines the type: Messages = Widen<typeof fr>, every other language is typed Messages, so a missing or extra key is a compile error, and MessageKey makes a typo in a key one too.

  • Files: src/i18n/<language>/<domain>.ts for fr, en, es, it and de (34 domains: topbar, timeline, inspector, export…, and news, the texts of the « Nouveautés » window), gathered by the index.ts of each folder. Key = domain.key. A message is a string or { one, other, … } plural forms picked by vars.count through Intl.PluralRules.
  • Runtime (i18n/index.ts): t(key, vars?) fills {name} placeholders; useT() re-renders a component when the language changes; withLanguage(code, fn); tRich (rich.tsx) for messages containing React nodes. Non-React code (overlay, export, errors) calls t directly.
  • Formats: numbers, dates and lists go through i18n/format.ts and ui/format.ts, never toLocaleString('fr-FR') or hand-built strings.
  • Module-level label tables use getters (get label() { return t('…') }) so they follow the language.
  • The language preference is a device preference (usePreferences), applied by installLanguage() from main.tsx only (so tests stay French); a first run follows the first browser language the app offers (else French).
  • Not translated: user data (track names, captions), OpenStreetMap names, units that read the same, developer-only text (console, diagnostic report, command-line output, the sample GPX, the web manifest, the service worker).
Where to look src/i18n/, ARCHITECTURE.md « Internationalisation » (rules and terminology table). Tests: src/i18n/i18n.test.ts (key and placeholder parity), format.test.ts, src/ui/LanguageMenu.test.tsx, e2e « langue ».

State management, summarised

See the mental-model part for the idea. In practice: project data goes in useAppStore (so it is saved and undone), transient data in a small store beside the module that owns it, and preferences of the device (theme, language, layout) in usePreferences and getPlatform().storage. Pure modules never import a store; components and hooks do. Components select the smallest value they need. Anything a frame needs from the store inside useFrame is read with useAppStore.getState() rather than a hook, so a store change does not re-render React.

Unit tests (Vitest)

A unit test calls one module with known inputs and checks the output; Vitest is the runner (like JUnit or pytest), configured in the test block of vite.config.ts.

  • Where: src/**/*.test.ts and *.test.tsx, next to the module they test, but not always under its name: the tests of scene/trackLineSet.ts are in TrackLines.test.tsx, those of overlay/themes.ts in overlay/settings.test.ts. Search with grep -rln functionName src --include='*.test.*'. Fixtures: __fixtures__/ folders.
  • Environment: node by default. A file that needs the DOM (a component, DOMParser, canvas) starts with // @vitest-environment jsdom (jsdom is a simulated browser). CSS is stubbed out in tests, except fonts.css.
  • A long test on purpose: src/flyover/filmAudit.test.ts replays the opening and closing shots of the 12 camera presets, with 4 shot styles, on 3 invented terrains (switchbacks and loops on a steep massif, a raid over hills) at 30 frames a second, and fails on any jolt, any frame too close to the ground and any marker out of the frame (the quick « Saut » shot is checked for everything but its pace). It has a timeout of its own (2 minutes). A change to the camera can pass every other test and still fail here: run it before and after.
  • Pool: one isolated worker thread per file (pool: 'threads'), about 6 s faster than forked processes according to the comment in the config.
  • Language: tests run in French (installLanguage() is only called from main.tsx), so they assert the French texts.
  • How things are isolated: pure modules take plain values; the terrain engine takes its dependencies as an argument (EngineDeps); network and the video encoder are faked; invoke of Tauri is an injectable parameter; stores are reset in beforeEach (resetAppStore()).
  • Run one file or one test: npx vitest run src/film/clock.test.ts, npx vitest run -t "pickRegionalImagery", or npx vitest for watch mode.
  • What is not tested automatically: how the 3D rendering looks, sound, export speed on a real GPU, and (per how-it-works.html) interface components beyond the ones with a .test.tsx; the manual list is Manual checks on a real machine.
Reading a failing test
  1. Read the first FAIL block, not the last: the file, the test title, then the diff (- Expected / + Received) and the line of the failing expect.
  2. Run only that file (command above) until it passes, then the whole suite.
  3. A TypeScript error shown by Vitest is not type checking (Vitest strips types): run npm run typecheck for those.
  4. If a test passes alone and fails in the suite, look for state kept in a module-level store or variable that the test did not reset.
  5. A timing failure under load: the suite runs files in parallel threads; retry with --maxWorkers=1. The history has fixes that gave slow tests explicit timeouts (3a7e98c).
  6. Do not « fix » a test by loosening it before you know whether the code or the test is wrong. Tests such as the clock continuity and « export equals preview » checks exist to catch exactly the mistakes this architecture invites.

Debugging and performance

  • Browser developer tools (F12 in Chrome or Edge): Console shows errors and the app's own logs ([export] lines during an export: render time breakdown, tile waits, encoder wait); Network shows tile, weather and Overpass requests (look for 4xx and 5xx, and for a missing Access-Control-Allow-Origin); Sources shows your TypeScript through source maps in development; Application shows localStorage (keys starting with openflyover.), Cache Storage and the service worker (use « Update on reload » or « Unregister » when testing it); Performance records a trace.
  • In the app: « Réglages » has a « Diagnostic » section: « Afficher le rapport » opens the « Rapport de diagnostic » (device, GPU, settings, no track names; kept in French on purpose) and a test export without encoding; the status bar shows fetch states and, on the desktop, memory and CPU; the export history lists the time and a summary of the settings of past renders (export/history.ts).
  • A camera jump, or a camera too close to the ground, in a film: replay it instead of judging by eye. auditFilmCamera (src/flyover/filmAudit.ts) places the camera of the film frame by frame (30 a second) and lists the problems with their time: jolt (the camera or its aim changes speed too abruptly), low (closer to the ground than MIN_TERRAIN_CLEARANCE_M) and marker-out (the marker leaves the frame). It is not a button of the app, it runs from a test. (1) Write down the track, the opening and closing shots, the camera preset and the film time of the jump. (2) In a throwaway test file next to filmAudit.test.ts, build the path (trackPathOf), the clock (filmClockFor) and a terrain height function like the ones of that test (steepSampler, hillySampler), then print auditFilmCamera(path, clock, frame, sample, options, { fromS, toS }) and run it with npx vitest run path/to/file --silent=false; each issue has a kind, a startS, an endS and a worst value. (3) Once the audit shows the problem, fix it and add the case to the scenes of filmAudit.test.ts so that it cannot come back; the whole battery (12 presets × 4 shot styles × 3 scenes, opening and closing) runs with npx vitest run src/flyover/filmAudit.test.ts and takes a while. Limits: the frames next to a change of shot or stop are not read, and the audit reads only the terrain heights it is given, not what the engine had loaded when the jump was seen, so a jump that shows up only while tiles are loading is a level-of-detail question, not a camera one.
  • Blank or white terrain: Network tab. A tile request failing, or an imagery source answering white tiles outside its coverage (the engine detects and replaces them), or CORS. Try another imagery source.
  • The 3D view does not update: the scene renders on demand. If a new store should trigger a redraw, check renderOnDemand.ts (wakeScene, sceneChanged); a hand-made change of a three.js object may need invalidate() from @react-three/fiber.
  • Slow preview: lower the cloud quality and the lens effects (the « poids de rendu » pictograms rank settings by cost, ui/renderCost.ts); check the pixel ratio (deviceBudget()); record a Performance trace and look at useFrame callbacks.
  • Export problems: read the message (it names the tile and the server), the [export] console lines and the diagnostic report; on a phone the tab may be killed for memory (export/guard.ts reports it at the next start).
  • Production-only bugs (service worker, base path, chunk loading): npm run build && npm run preview; for a sub-path deploy, build with BASE_PATH=/x/.
  • Desktop-only bugs: npm run tauri:dev, and run cargo test --locked in src-tauri/. Remember a missing host in the CSP or a missing capability fails silently or with a console error in the web view.

From an issue to a pull request

The words. An issue is a numbered note on GitHub that describes a bug or a wish (« #188 »). A branch is your own line of commits, separate from master until it is merged. A pull request (PR) is the request to merge that branch into master: GitHub shows the changes, runs the automatic checks (CI) on them, and merges when you press the button. The open issues of the repository carry « Leads to investigate » and « More help — step by step » comments built on the method below. It works for any bug or small feature.

  1. Start from an up-to-date master, on a new branch. git switch master, git pull, then git switch -c fix/188-short-name (feat/… for a feature, docs/… for documentation).

    You should see Switched to a new branch 'fix/188-short-name'.

  2. Reproduce, and write down what you see before reading code: the exact steps, a screenshot, the style or preset used. Play the film twice: a problem seen only on the first playback comes from tiles still loading (level of detail); one that stays is in the logic.
  3. Find the chain from what you see to the function behind it: a French label on screen, its key in src/i18n/fr/ (search the text), the component in src/ui/ that uses the key, the setting in src/state/store.ts, the module that computes (Where do I find …). Components only wire things together; the decision is almost always in a pure function of a .ts file.

  4. Find its tests (not always under the module's name) and run them alone: npx vitest run path/to/file.test.ts. They tell you what the function promises today.

    You should see them pass: the bug is a case the tests do not cover yet.

  5. Measure before changing: a throwaway test file that calls the function with your case and prints the values (console.log, console.table; add --silent=false if nothing shows), or a temporary log in the running app. Do not commit it. The numbers choose your thresholds and prove the fix afterwards.

  6. Write the failing test, then the change, within the repository's rules: no state between frames, a new Track field is optional and handled by both halves of project/document.ts, a new setting follows the recipe.

    You should see the new test fail first (a FAIL block with - Expected / + Received: how to read it), then pass after your change.

  7. Check every consumer: search the function and the pattern it relies on (for heights, ?? at.ele); npm run typecheck lists every Record table and language file that misses a new id.

  8. Close the loop: npx vitest run, npm run typecheck, npm run lint, the manual check of the second step, then the docs (CHANGELOG.md under ## Unreleased if users can see the change, ARCHITECTURE.md if a contract or a documented value changes). If an issue comment pointed to the wrong place, say so in the issue.

    You should see all tests pass, no type error, no lint line marked error, and the problem gone in the app.

  9. Commit, push, open the pull request. git status (check that only your files changed), git add with those files, git commit -m "fix(scene): fix #188, what changes for the user" (the prefixes are in The commands), git push -u origin fix/188-short-name, then open the pull request on GitHub (or gh pr create). Writing Fixes #188 in its description closes the issue when it is merged.

    You should see the CI checks start on the pull request (lint, test, build, and rust when src-tauri/ changed) and turn green. Then merge it; the website updates on its own.

What a « setting » is in this app

A setting is one value of the project that the user chooses in a panel: a checkbox, a slider, a list. Think of the project as a saved form: each setting is one field of that form. Every setting has a name in the code (cloudShadows), a type (here true or false), and a default value, the value a new project starts with.

All the settings live together in one object called Settings, kept in the app's shared memory, the store. Panels read it and change it; the 3D view and the film read it to draw; « Enregistrer » writes the whole object into the project file; opening a file reads it back and checks every value. Because all of this works over the whole object, a new setting is saved, undone (Ctrl+Z) and checked without writing any code for it. That is why adding one only touches a handful of places.

What it is. A normal setting has one value for the whole film. Add an export format

What it is. The export turns the film into a file: a video (a frame size, an aspect ratio, a codec and a container), a still image or a poster. When you need it: to offer a new frame shape (3:2), a new video format, a new poster size or a new kind of output. Most lists are declared once and everything else (the menus, the checks of older projects, the command line) follows. Background: The export pipeline.

A new aspect ratio (for example 3:2):

  1. src/export/schedule.ts: add { id: '3:2', get label() { return t('video.aspect.3:2') }, x: 3, y: 2 } to VIDEO_ASPECTS. VideoAspect, videoSize, isValidVideoSettings, the top-bar selector, the stage framing, the safe zones, the batch formats and the command line (KNOWN_FORMATS in cliRender.ts) all derive from this list.
  2. the video.ts of each language in src/i18n/: the key aspect.3:2. The format icon is drawn from the ratio (AspectIcon).
  3. Tests: src/export/schedule.test.ts (sizes), batch.test.ts if formats are enumerated there, and an overlay check at that ratio if the layout has special cases.

A new codec or container. src/export/encoder.ts: add a CodecCandidate to CODEC_CANDIDATES (preference order), a bitrate factor in CODEC_BITRATE_FACTOR, an entry in VIDEO_CODEC_CHOICES (schedule.ts) and CODEC_NAMES (with its i18n key), and audio candidates in AUDIO_CANDIDATES. A new poster size: one entry in POSTER_FORMATS (src/poster/settings.ts, pixel size at 300 dpi) and its poster.format.<id> message; the layout is computed from the size.

A new platform chip, or a new word for the file name. A new word of the file name template is added to expandNameTemplate in the same file, with a test in schedule.test.ts.

A new kind of output (one that is not a video file): implement the VideoEncodeSession contract (addFrame, finish, codec, extension) next to encoder.ts and choose it where ExportController builds the session (next to createExportEncoder of nativeEncoder.ts); the rest of runExport does not change. Upgrade a dependency

What it is. The project uses outside libraries (npm packages for the web side, crates for the Rust side) at exact versions written in the lock files. Upgrading means moving one of them to a newer version. When you need it: for a security fix, a bug fixed upstream, or a feature you need; not by habit. Move one package or one family at a time, so that a breakage has one suspect.

  1. Look at what is out of date: npm outdated. Ranges in package.json are carets (^), except TypeScript, pinned to ~6.0.2. Read the release notes of the package, especially for majors.
  2. Change one package or one family at a time: npm install <pkg>@<version> updates package.json and package-lock.json; commit both. Families that move together: three, @types/three, @react-three/fiber, drei, postprocessing, @takram/* (the 3D stack is the fragile one: check peer dependencies); @heroui/react, @heroui/styles, react-aria, react-aria-components; tailwindcss and @tailwindcss/vite; vitest and @vitest/coverage-v8; react, react-dom and their @types.
  3. Run the full gate: type check, lint, unit tests, npm run build (watch the chunk sizes and the warning limit of 800 kB), then npm run e2e, then look at the 3D view and a short export by eye (rendering is not unit-tested; manual checks).
  4. Rust and Tauri: @tauri-apps/api, @tauri-apps/cli and the plugins on the npm side move with the tauri and tauri-plugin-* crates in src-tauri/Cargo.toml; update both sides together (the repository does not state the exact compatibility rule: read Tauri's release notes). cargo update -p <crate> changes Cargo.lock; CI runs cargo test --locked, which fails if the manifest and the lock disagree. Mind rust-version = "1.77.2": sysinfo is held at 0.36 because it is the last release for that Rust version (comment in Cargo.toml).
  5. A dependency change alters the licence inventory: npm run notices before the next release. mediabunny is MPL-2.0: modifying its files obliges you to publish the modifications.

Bump the version and release

What it is. A release is a new version number (3.0.0 → 3.1.0) given to what is on master, with three results: the website shows the new version, installers for Windows, macOS and Linux are built and published on GitHub, and installed desktop apps can update themselves. When you need it: when enough changes have gathered in CHANGELOG.md under ## Unreleased for users to benefit. Numbers follow the usual rule: the last digit for fixes only, the middle one for new features. The full procedure, with every detail, is Release procedure; this is the short path. X.Y.Z below stands for the new number.

  1. Check that master is healthy. git switch master, git pull, then npm ci, npm run typecheck, npm run lint, npx vitest run --maxWorkers=1, npm run build and OPENFLYOVER_E2E_SKIP_EXPORT=1 npm run e2e.

    You should see every command finish without an error. Then make the release branch: git switch -c release/X.Y.Z.

  2. Write what changed, for users. In CHANGELOG.md, rename ## Unreleased to ## X.Y.Z (Month Year). Then the « Nouveautés » window (the « what's new » dialog inside the app): a block first in WHATS_NEW (src/ui/whatsNew.ts) and its news.vNN.* texts in the news.ts of each of the five languages. Nothing reminds you of this one: do not forget it.

  3. Change the number in five places. npm version X.Y.Z --no-git-tag-version updates package.json and package-lock.json; edit by hand version in src-tauri/Cargo.toml and in src-tauri/tauri.conf.json, and the openflyover entry of src-tauri/Cargo.lock (or let a cargo build in src-tauri/ refresh the lock file).

    Run git grep -n "X.Y.Z" with the real number. You should see the five files and the changelog heading; git grep -n "old number" should only find mentions of the past (older changelog entries, the previous « Nouveautés » block, documents).

  4. Licences, only if a dependency changed since the last release: npm run notices (about 8 minutes the first time).

  5. Pull request, then merge. Commit (chore(release): X.Y.Z), push, open the pull request, wait for CI, merge.

    You should see the « Website » workflow run on master in the Actions tab of GitHub, and the site serve the new version a few minutes later.

  6. Tag the merge commit to build the installers: git switch master, git pull, git tag -a vX.Y.Z -m "OpenFlyover X.Y.Z", git push origin vX.Y.Z. A tag is a permanent name on one commit; this one starts the « Desktop installers » workflow.

    You should see that workflow run on Windows, macOS and Ubuntu, then the release « OpenFlyover vX.Y.Z » appear on GitHub with the installers. If one system fails, the release stays a draft: re-run the failed job.

Verify
  • git grep -n "X.Y.Z" finds the five places and the changelog; nothing still says the old number.
  • cargo test --locked passes (the lock file matches the manifest).
  • After the tag: three installers on the release, the website shows the update prompt.

Glossary

Web, 3D and Rust terms in the sense they have here, then the project's own vocabulary, including the French words of the interface (the French text is the reference; the English interface follows the terminology table of ARCHITECTURE.md).

Web and tooling

Bundler

Tool that merges many source modules into few optimised files and splits rarely used code into on-demand chunks. Here: Vite (Rolldown).

Chunk

One output file of the bundler, loaded on demand through import().

DOM

The tree of elements of the page that the browser draws. React updates it for you.

ES module

JavaScript's native module system (import / export); the whole code base uses it.

HMR

Hot module replacement: the dev server swaps a changed module in the running page without a reload.

Lock file

package-lock.json, Cargo.lock: exact versions of every dependency, committed.

Lint

Static analysis for risky or inconsistent code. Here oxlint.

jsdom

A simulated browser in Node, used by tests that need a DOM.

Promise / async

A value that arrives later (a future); await pauses the function until it does, without blocking the page.

Service worker

A script that sits between page and network and can answer from a cache. Website only: platform/serviceWorker.js.

Static site

A folder of files served as they are; all logic runs in the visitor's browser.

Cache Storage

Browser store of responses keyed by URL; here the offline tiles and « Mes projets ».

CORS

The browser rule that a page may read a response from another site only if that site allows it with a header. Every tile source must send it.

CSP

Content security policy: the list of origins a page may load from or contact. Set for the desktop app in tauri.conf.json.

React and interface

Component

A piece of the screen written as a function: it receives inputs (props) and returns what to show, in an HTML-like notation. A checkbox with its label is a component; a whole panel (LightSettings) is one too, made of smaller ones.

Props

The inputs of a component, written like HTML attributes: in <Checkbox checked={cloudShadows} onChange={…}>, checked and onChange are props. Like the arguments of a function call.

State

Data that, when changed, makes the interface redraw. Local (useState) or shared (a store).

Hook

A function named use… that a component calls to get memory or a connection to the outside: useAppStore(…) reads the store, useT() gives the translation function. Call hooks at the top of the component, never inside an if (the lint checks it).

Effect

useEffect: code run after render, with a cleanup, to talk to the outside world.

JSX / TSX

HTML-like notation inside JavaScript / TypeScript; the file extension is .tsx.

Selector

The small function you give the store to say which value you want: (s) => s.settings.cloudShadows reads « given the store s, give back its settings.cloudShadows ». The component is redrawn only when that value changes.

Store (zustand)

The app's shared memory: one object holding the tracks, the settings and the playback, plus the functions (actions) that change it. Panels, the 3D view and the export all read the same one, so a change made in a panel is seen everywhere. Here useAppStore (src/state/store.ts, made with the zustand library) and about twenty smaller ones.

Suspense / lazy

On-demand loading of a component with a placeholder while it loads.

StrictMode

A development mode that runs effects twice to expose leaks.

Primitive

The project's wrapper of a HeroUI component, in src/ui/primitives/.

Token

A named design value (colour, radius, spacing) in theme.css.

Utility class (Tailwind class)

A short class name that sets one thing of an element's look: gap-2 (spacing), text-hint (text size), rounded-sm (corners). The look of a component is the list of such classes in its className. @utility names a repeated combination (The UI layer).

React Aria

Adobe's headless components for keyboard, focus and screen-reader behaviour, under HeroUI.

3D, video and sound

WebGL

The browser's API to the graphics card.

Shader

A small program that runs on the GPU per vertex or pixel.

Mesh

A surface made of triangles; a terrain tile is a 65 × 65 vertex grid plus skirts.

Texture

An image painted on a mesh; here the composed aerial photo of a tile.

Scene graph

The tree of objects three.js renders.

Render loop

The per-frame cycle: update, draw. Here on demand (frameloop="demand").

Post-processing

Image effects applied after the scene is drawn (haze, tone mapping, grading, bloom).

LOD

Level of detail: finer tiles near the camera, coarser far away. Here a quadtree.

DEM

Digital elevation model; here elevation tiles decoded from colours (Terrarium).

Tile (XYZ)

A square map image addressed by zoom z, column x, row y; y = 0 at the north.

Draping

Laying the track line on the ground: each point takes the terrain height under it, or its recorded elevation where no terrain is loaded, times the exaggeration, plus a 3 m lift (computeDrapedPositions).

Skirt

Edge of a tile lowered below the ground to hide cracks between detail levels.

ECEF / local frame

Earth-centred coordinates; the local tangent frame the scene uses (X east, Y up, Z south).

Geoid / MSL

Mean sea level surface; heights are above it (geo/geoid.ts).

Canvas 2D / OffscreenCanvas

A drawing bitmap with 2D commands; the overlay and the poster are drawn on one.

Frame / fps

One image of the film / images per second (24, 30, 60).

Codec / container

The compression of video or sound (H.264, VP9, AAC, Opus) / the file format that holds the streams (MP4, WebM).

WebCodecs

Browser API to the system's encoders. mediabunny writes the container.

Loudness (LUFS)

How loud a soundtrack is heard to be, measured in LUFS (the unit of the ITU-R BS.1770 standard). Platforms play films at a similar level, so « Normaliser le volume » brings the sound to −14, −16 or −23 LUFS and keeps the peaks under −1 dB (film/loudness.ts).

Image sequence

An output made of one numbered image per frame (name_00001.png, name_00002.png…) instead of a video file, for an editing application. « Séquence d'images PNG » (export/sequenceEncoder.ts).

ffmpeg

A command-line video tool; used by the Linux desktop app where WebCodecs is missing.

SwiftShader

Software GPU used by headless Chromium in tests: correct, slow.

Rust and Tauri

Crate

A Rust package, library or program.

Cargo

Rust's build tool and package manager (Cargo.toml, Cargo.lock, cargo test).

Tauri

Framework showing a web site in a native window with a small Rust backend.

Web view

The operating system's own browser engine inside the window (WebView2, WebKit, WebKitGTK).

Command

A Rust function the page can call with invoke (#[tauri::command]).

Plugin

Packaged native feature: dialog, fs, oauth, opener, and for updates updater and process.

Capability / permission

The allow-list of what the window may call; capabilities/default.json.

IPC

Inter-process communication between the web view and the Rust process.

fs scope

The set of paths the page may read or write; grown by dialogs and by cli.rs / opened.rs.

Track

The imported recording (GPX or FIT) as a Track. Rail tab « Trace ».

Progress

0 to 1: fraction of the track's distance where the marker is.

Film time

Seconds at ×1 from the very first frame, opening included. playback.timeS.

Film clock

The pure mapping from film time to phase and progress (film/clock.ts).

Flyover (« Survol »)

The camera flight along the track; the tab of the camera settings.

Pacing

Slow-downs and pauses along the flight (flyover/pacing.ts).

Shot (« Plan »)

Opening or closing camera move: « Ouverture », « Clôture ».

Stop / hold (« Arrêt »)

A pause of the film at a place, with its own camera; automatic stops at highlights.

Speed portion

A section of the track flown faster or slower (film.speeds).

Keyframe (« Image clé »)

A saved camera view along the track; also parameter keys (speed, exposure, sun hour, grading, 3D labels) and marker keys.

A row of the timeline: « Plans », « Arrêts », « Textes », « Médias », « Musique », « Marqueur », « Étiquettes », « Étapes ». Each lane can be folded to a thin strip and locked (its blocks no longer move); the choice is kept on the device, not in the project (ui/laneState.ts).

A stretch of the timeline marked with an in point and an out point (keys I and O). The preview loops inside it so that you can work on a few seconds; it is not saved and the export still renders the whole film (film/workArea.ts).

Small frames of a video clip drawn along its block on the timeline, to find a moment without playing it. Read once per clip, never saved (ui/Filmstrip.tsx).

An edit that moves what follows so that no gap is left: Shift+Delete on a block, or Shift held while dragging its end, shifts the later blocks of the same lane by the same amount (rippleRemove, rippleDrag in film/timeline.ts).

A replay of a film frame by frame that measures jolts of the camera, a camera too close to the ground and a marker leaving the frame. Run from a test, not from the interface (flyover/filmAudit.ts; Debugging).

Everything drawn over the 3D image; the tab of its settings. « Afficher l'habillage » (overlay.enabled) shows the live widgets only; the titles have their own switches and the timeline texts always show (drawOverlay in overlay/draw.ts).

Lens (« Objectif »)

Motion blur, bloom, lens flare, depth of field, all off by default.

Poster (« Affiche »)

Printable poster of the outing (A4, A3, square, 300 dpi).

Stage (« Étape »)

One track of a sequence. « À la suite »: stages flown one after the other. « En parallèle »: ghost race.

« À la suite », the transition and the stage card set once for all stages in « Trace › Plusieurs traces » (junctionDefault); a transition or card changed from its block on the timeline stores only what differs (hasOwnTransition, hasOwnCard, StoredStageCard in film/junctions.ts).

Transition between two stages, three choices: « Passage » (« Coupe », « Fondu au noir », « Fondu au blanc »), « Passer la nuit » (when the stages are on two days) and « Revoir l'étape finie ». It always plays as chosen (junctionPlan in film/junctions.ts).

Chaining (« Enchaîner »)

Merging several tracks into one route.

Planned outing (« Prévoir la sortie »)

Estimated times for a route without times.

Offline pack (« Hors ligne »)

Tiles of a corridor along the track kept for use without a connection.

Presets (« Préréglages »)

Named sets of settings the user saves and applies in one click, either all settings or one family (« Carte et ambiance », « Trace, marqueur et étiquettes »…: PRESET_SCOPES; the settings of each family in PRESET_SCOPE_KEYS, src/project/presets.ts).

My projects (« Mes projets »)

Projects kept inside the app, with thumbnails.

« Modifié »

The marker of a setting or section that differs from its default: a round ↺ button (ModifiedMarker) that resets it.

Render weight (« poids de rendu »)

The pictogram that tells how much a setting lengthens the export (ui/renderCost.ts).

Export quality

« Standard / Haute / Maximale »: bitrate and cost of the effects at export time.

« Carte alpine »

The visual identity of the app: map paper, ink, trail-marker red, glacier, moss (src/ui/theme.css).

D+, Col, Sommet, Refuge

Elevation gain, pass, peak or summit, mountain hut (not a UI mode).

Safe zones (« Zones de sécurité »)

Guides showing the margins of a social-network format; key G.

Words used in the recipes

Setting (« réglage »)

One value of the project chosen by the user in a panel, like one field of a saved form. All of them form the Settings object, saved in the project file.

Here interface Settings and DEFAULT_SETTINGS in src/state/store.ts; recipe: Add a setting.

Default value

The value a setting has in a new project, and the value used when a file lacks the setting or holds a wrong one. The ↺ button of its section puts it back.

Here DEFAULT_SETTINGS in src/state/store.ts.

Type, interface

A type says what kind of value a name holds (boolean: true or false; number; string: text). An interface lists the fields of an object with their types, like a C struct. TypeScript checks them before the program runs, then removes them.

Here interface Settings; the checker is npm run typecheck.

Type check

The compiler reads every file and reports names and types that do not match (a typo, a missing translation, a missing field), without running anything. Errors look like file(line,column): error TS2741: ….

Here npm run typecheck.

Action

A function of the store that changes it. The panels never edit a value directly; they call an action, which also makes the undo step.

Here setSetting('cloudShadows', on).

Validation

Checking a value read from outside (a project file, a preset) before using it. A refused value is replaced by the default, with a warning, never a crash.

Here sanitizeSettings and SETTING_CHECKS in src/project/document.ts.

Upgrade and migration

Code that turns data saved by an older version into the current shape, so old files keep opening. An upgrade fills in fields added to one setting since; a migration converts a whole file from one format version to the next, and is rare.

Here SETTING_UPGRADES, MIGRATIONS and PROJECT_VERSION in src/project/document.ts (details).

Translation key (i18n key), domain

The name a screen uses to ask for a text: 'light.atmosphere.cloudShadows'. The first part is the domain, the file the text lives in (light.ts); the rest is the key inside it. « i18n » is short for internationalisation.

Here src/i18n/<language>/<domain>.ts; used with t('…').

Getter

A field written get label() { return t('…') }: its value is computed each time it is read instead of once. Used for labels kept in tables, so that they follow a change of language.

Pure function

A function whose result depends only on its arguments and which changes nothing else, like a maths function. Easy to test, and what makes the export identical to the preview. Pure modules never read the store; the caller passes the values.

Here most .ts files of geo/, flyover/, film/, overlay/.

Section (PanelSection)

A foldable block of a tab with a title and controls. Its keys list the settings it owns: they drive the ↺ « modifié » button of its head.

Here src/ui/PanelSection.tsx.

Unit test, test file

A small program that calls one part of the code with known inputs and checks the result. Files end in .test.ts or .test.tsx, next to the code they test.

Here npx vitest run <file> runs one file (Unit tests).

Branch, commit, pull request

A commit is one saved change; a branch is a line of commits apart from master; a pull request asks to merge a branch into master, after the automatic checks (CI) pass.

Here From an issue to a pull request.

npm run …, npx …

npm run typecheck runs a command named in the scripts of package.json; npx vitest runs a tool installed in node_modules/ by npm ci. Both are typed in a terminal opened in the repository folder.
