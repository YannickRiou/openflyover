How to use this handbook

This is the page to read if you inherit OpenFlyover and have to keep it alive alone: understand how it was made, find your way in the code, change a setting, fix a failing test, publish a release. It does not repeat what other documents of the repository already say well: it points to them.

If you know the web already

Skip the explanations of part 3 and go to the repository tour, the domains and the recipes.

If you come from classic software

Read in order. Part 3 is the dictionary: each web notion is compared to something you know (a build tool, a state machine, a thread, a database) and then shown in this repository.

If something is broken now

Jump to day-to-day (commands, reading a failing test, debugging) and to the pitfalls list in its last section.

02

Genesis and history

OpenFlyover makes a 3D flyover film from a GPX or FIT track recorded on an outing (hike, run, ride, ski tour). The track is laid on real terrain covered with aerial photos; a virtual camera flies along it; the person edits the film on a timeline and exports a video, a still image or a printable poster. Everything runs on the user's machine: no account, no API key, no paid service, no application server.

Ten days of git history

The history in this repository runs from 5 to 15 October 2026: 608 commits at version 2.2.0. The first commit already contains the whole skeleton (geo maths, import, terrain engine, scene, store, sample track); everything else grew on it in the phases below. The phase names come from the headings of ARCHITECTURE.md (« phase 2 » to « phase 7 ») and from the commit messages.

A mental model for a developer new to the web

This part translates the web vocabulary into what you already know, then shows each notion in this repository. Read the analogies as a first approximation: where one misleads, the text says so.

The browser is the runtime, the web page is the program

A desktop program is compiled for an operating system and calls its libraries. A web application is delivered as files (JavaScript, CSS, images) that a browser downloads and runs. The browser provides everything the program needs: a UI toolkit (HTML and CSS), 2D and 3D drawing, audio, video encoding, networking, local storage, file saving. OpenFlyover uses a large share of that platform: 3D (WebGL), 2D canvas, video encoding (WebCodecs), audio mixing, Cache Storage, a service worker.

Analogy The browser is a virtual machine with a very large standard library and a GUI toolkit built in. The « executable » is a folder of text files; « installing » is downloading them. The user's machine is the server of everything the app does.

In this repository. index.html is the only page: an empty <div id="root"> and a script tag for /src/main.tsx. src/main.tsx installs a few global services (appearance, language, offline tiles, export guard, service worker) and mounts the React tree. The desktop application is the same page shown in the web view of the operating system by Tauri.

HTML, CSS, JavaScript, TypeScript

HTML

The tree of elements the browser displays (the DOM). Here it is almost empty: React builds the elements from code.

Here index.html, plus an inline script that sets the theme before the first paint to avoid a flash.

CSS

Rules that give elements their look and layout. Think of it as a declarative styling language with inheritance and a cascade (later and more specific rules win).

Here src/ui/theme.css (tokens), utilities.css, primitives/*.css; see the UI layer.

JavaScript

The language of the page: dynamically typed, single-threaded, event-driven, with async/await on top of promises (futures). The browser runs one main thread that handles input, drawing and your code in turns.

Here a few .mjs tools (scripts/, e2e/run.mjs) and src/platform/serviceWorker.js; everything else is TypeScript.

TypeScript

JavaScript plus static types, checked by a compiler before the program runs and erased afterwards: no type exists at run time. Closest to a gradually typed language with a structural type system (two types are compatible when their shapes match).

Here every file of src/ is .ts, or .tsx when it contains JSX (HTML-like notation used by React).

The TypeScript settings that shape how you write code are in tsconfig.app.json:

npm, package.json, Vite: the build chain

Node.js and npm

Node runs JavaScript outside a browser: here only for development tools (build, tests, scripts), never at run time. npm is the package manager: package.json is the manifest, package-lock.json the lock file with exact versions and hashes, node_modules/ the local install (ignored by git). Like Maven or Cargo.

Here npm ci installs exactly the lock file (use it, not npm install, unless you mean to change dependencies). "type": "module" makes .js/.mjs files ES modules. "private": true prevents an accidental publish.

Vite (build tool and dev server)

In development it serves your source modules to the browser one by one and reloads the changed one (hot module replacement): no build step to wait for. For production it bundles hundreds of modules into a few optimised files, splitting rarely needed code into separate chunks loaded on demand. Vite 8 bundles with Rolldown (note the rolldownOptions key in the config).

Here vite.config.ts: plugins react(), tailwindcss() and two local ones (below); base from BASE_PATH (GitHub Pages serves under /openflyover/, pages.yml sets it); test block for Vitest.

Code splitting and import()

A dynamic import('./X') is an on-demand load: the bundler emits a separate file, fetched when the line runs. It is how a 3 MB library stays out of the first screen. Comparable to lazy-loading a plugin DLL.

Here React.lazy(() => import(...)) for the 3D scene (src/ui/Stage.tsx), the export drawer and the offline panel (src/App.tsx), the atmosphere (FlyoverCanvas.tsx); import('mediabunny') in export/encoder.ts; the FIT reader in import/index.ts. See ARCHITECTURE.md « Loading ».

React: components, props, state, hooks, effects

React builds a user interface from components: functions that receive inputs (props) and return a description of what to show (JSX). You never edit the screen yourself. You change state, React calls your component functions again, compares the new description with the old one, and updates only what differs.

Analogy An immediate-mode UI with a diff engine: the screen is a pure function of the state, re-evaluated on change. The model-view-controller of classic desktop code is still there, only spread differently (table below).

State

Data a component remembers between calls (useState), or data shared by many components (a store). Changing it schedules a new render. It must be changed by replacing values (new object, new array), never by mutating them: React and the store detect change by reference.

Hooks

Functions whose name starts with use that give a component memory and lifecycle: useState, useMemo (cache a computed value), useRef (a mutable box that does not trigger a render), useEffect (run code after the screen updated, with cleanup). Rule: call hooks unconditionally, at the top level of a component; oxlint enforces it (react/rules-of-hooks is an error in .oxlintrc.json).

Effects

useEffect(fn, deps) runs fn after render and again when a dependency changes; its return value is the cleanup. It is where a component talks to the outside (subscribe, fetch, create a GPU resource). Think of it as a constructor/destructor pair tied to some inputs. In development StrictMode runs it twice on purpose to catch leaks: TerrainLayer.tsx says why it creates the terrain engine in the effect and disposes it in the cleanup.

lazy() declares a component loaded on first use; <Suspense fallback=...> shows a placeholder meanwhile. Used for the 3D scene, the export drawer and the atmosphere.

State management: one store, selectors, pure modules

The app state lives in a zustand store, a small library: create() returns a hook (useAppStore) that holds an object and its actions. A component calls it with a selector ((s) => s.settings.exposureEv) and is re-rendered only when that selected value changes. Outside React the same store is read with useAppStore.getState() and watched with useAppStore.subscribe(...).

Analogy A single in-memory, observable application model with typed commands (actions) and queries (selectors). Subscribing with a selector is like a SQL view over it; a change notification fires only when the view's result changed.
  • The main store is useAppStore in src/state/store.ts: tracks, derived bounds and frameOrigin, settings (one Settings object holding every user setting, with the film inside it), playback (progress, film time, speed), project name, selection.
  • Settings are replaced, not edited: setSetting(key, value) does set({ settings: { ...get().settings, [key]: value } }). That new object is what undo (src/project/history.ts, which compares snapshots) and the « Modifié » marker (isProjectDirty in src/ui/shell.ts, by reference) rely on.
  • Twenty other small stores hold what is not a project setting: export progress (export/store.ts), weather, landmarks, water, region, offline packs, media table, music preview, toasts, preferences, project library… Each is a create() in its own module.
  • Pure modules do the computing: geo/, import/, terrain/, flyover/, most of film/, overlay/, weather/, poster/layout.ts take values and return values (no React, no store, no DOM; the headers say « Pure functions »). They are the easy part to test and the part the export reuses.

Three.js, react-three-fiber, WebGL, the render loop

GPU and WebGL

The GPU is a massively parallel processor that draws triangles. WebGL is the browser's API to give it work (an OpenGL ES profile). You upload geometry and textures, and write small programs called shaders that run per vertex and per pixel. Comparable to a compute device with its own memory and its own language.

Three.js

A library that hides most of WebGL behind a scene graph: a tree of objects (groups, meshes, lights, a camera). You change object positions; the library renders the tree. The unit of drawing is a frame: one image.

react-three-fiber (R3F)

Lets React components describe that scene tree: a component returns three.js objects, and hooks give access to the renderer. useFrame(cb) registers a callback run on every frame (the render loop). Here three.js is 0.186 and fiber 9.

The render loop

A game loop: input, update, draw, about 60 times a second. R3F can run it continuously or on demand (frameloop="demand"): it draws only when something asks. OpenFlyover is on demand (below) to save power when nothing moves.

In this repository. The 3D view is <Canvas> in src/scene/FlyoverCanvas.tsx:

<Canvas gl={gl} camera={CAMERA} dpr={[1, BUDGET.maxPixelRatio]} frameloop="demand" flat shadows="percentage" ...>
  {hasTracks && (
    <TerrainLayer>
      <RenderOnDemand />
      <TrackLines />
      <WaterLayer />
      <FlyoverRig />
      <CameraRig />
      <Labels />
      {atmosphere && (<Suspense fallback={null}><AtmosphereLayer /></Suspense>)}
      <ExportController drawOverlay={overlayDrawer.draw} />
    </TerrainLayer>
  )}
</Canvas>
  • TerrainLayer creates the terrain engine (src/terrain/engine.ts, no React) and shares it with its children through a context (useTerrainContext). Children are layers: the track, water, labels, the rig that moves the camera and marker, the atmosphere (sky, clouds, post-processing) and the export controller. The scene is mounted only once there is a track (hasTracks).
  • On-demand rendering. src/scene/renderOnDemand.ts asks for frames while the film plays, tiles load or the camera fits, and for WAKE_FRAMES = 30 frames after any change of the stores the scene reads (wakeScene()). The time step is capped (MAX_FRAME_DELTA_S = 0.25 s) so playback does not jump after a pause. During an export the loop is switched off (frameloop 'never') and ExportController draws each frame itself.
  • FlyoverRig is the heart: on each frame it reads progress and film time from the store, computes the camera view with a pure function (computeFilmView, reached through filmViewAt in scene/filmView.ts) and places camera and marker.
  • The Canvas needs a GPU. Without one (CI, e2e) Chromium falls back to a software renderer (SwiftShader): correct but slow, so the e2e run uses long timeouts.

Canvas 2D and OffscreenCanvas

A <canvas> is a bitmap you draw on with commands (lines, text, images), like a software GDI or Cairo surface. OffscreenCanvas is the same without being on screen. Here the film overlay (titles, counters, profile, mini-map, credits) is painted by the single function drawOverlay(ctx, frame, settings, size, assets, extras) in src/overlay/draw.ts. The preview calls it on a transparent canvas laid over the 3D view (OverlayCanvas.tsx, redrawn on the next animation frame after a store change); the export calls it on an OffscreenCanvas for every frame (composeFrame in src/export/capture.ts). The poster uses the same approach (src/poster/draw.ts). All sizes derive from the frame size (1 unit = 1 % of the shorter side), so any resolution works.

Web Workers: none, on purpose or by default

A Web Worker is a background thread with no access to the page, communicating by messages. This project starts none (no new Worker anywhere in src/). Heavy work runs on the main thread, and two mechanisms keep the page responsive: the browser itself decodes images off-thread (createImageBitmap in terrain/fetch.ts) and the export yields to the event loop once per frame (yieldToEventLoop in export/capture.ts). If you ever need a worker, Vite supports new Worker(new URL('./w.ts', import.meta.url), { type: 'module' }); nothing here prepares for it. The only worker-like thing is the service worker.

The service worker (website only)

A service worker is a script the browser keeps registered for a site; it sits between the page and the network and can answer requests from a cache, like a local reverse proxy that survives page reloads. It is what makes the site installable and usable offline once loaded. Here src/platform/serviceWorker.js (built into sw.js by vite.config.ts) precaches the app shell at install, caches the 12 MB of sky and cloud textures on first use, never touches cross-origin requests (tiles, weather: the app has its own tile cache) and keeps the files of an Android « share target » for the page. src/platform/webApp.ts registers it (production, HTTPS, never inside Tauri) and shows « Nouvelle version disponible ». Rule written in the file header: it never deletes the caches of the app itself (offline packs, projects).

WebCodecs, mediabunny and the audio pipeline

WebCodecs is a browser API to the system's video and audio encoders (VideoEncoder), fast and often hardware-backed. It produces compressed frames, not files. mediabunny (an npm library, MPL-2.0) writes them into an MP4 or WebM container, like a muxer in ffmpeg. Here src/export/encoder.ts picks the first codec the machine can encode (CODEC_CANDIDATES: H.264 in MP4, HEVC in MP4, VP9 in WebM, VP8 in WebM), streams the file to disk when the platform allows, and loads mediabunny lazily. Sound is mixed by film/audio.ts with an OfflineAudioContext over the exact film length, so the mix is deterministic, never real time. Where the web view has no WebCodecs (Linux desktop), export/nativeEncoder.ts sends raw frames to the system ffmpeg through Rust (next part).

Since 2.0.0 the interface is built from Tailwind CSS 4 utilities and HeroUI 3 components. The rules and their reasons are in ARCHITECTURE.md (« Primitives » and « Styling »); this is the working summary.

Tailwind utilities

Instead of writing a CSS rule per component, you put small single-purpose classes on the element (flex, gap-2, text-hint, rounded-sm). A build step reads your sources and generates only the CSS for the classes you used. Comparable to composing from a fixed vocabulary of style atoms; the scale (spacing, type, colour) is the shared design system. Variants prefix a class for a condition: hover:, touch:, phone:.

The palette, fonts, radii and shadows of the app are CSS variables declared once in src/ui/theme.css (@theme static { --color-ink: ...; }), which also makes bg-ink, text-accent or font-heading exist. The Rust and Tauri part

The website is enough for most people. The desktop application exists for what a web page cannot do well: write a very long film straight to disk, open a .opnflvr project with a double-click, encode video on Linux where the web view has none, render a folder of tracks from a terminal, read the machine's memory and CPU load. It is a thin native shell around the same built site.

Tauri in plain terms

Tauri

A framework that opens a native window containing a web view (the operating system's own browser engine: Edge WebView2 on Windows, WebKit on macOS, WebKitGTK on Linux) and loads your site into it. A small Rust program runs next to it. Comparable to Electron, but with the system's engine instead of a bundled Chromium and Rust instead of Node as the native side.

Here Tauri 2 (src-tauri/Cargo.toml, @tauri-apps/cli and @tauri-apps/api in package.json).

Rust, crate, Cargo

Rust is a compiled language with ownership-based memory safety (no garbage collector, no null: Option<T>; errors are values: Result<T, E> and the ? operator). A crate is a package (library or program). Cargo is its build tool and package manager: Cargo.toml is the manifest, Cargo.lock pins versions (committed: about 520 locked crates), cargo build, cargo test, target/ is the build output (git-ignored). Like Maven and its repository, with the lock file always kept.

Tauri command and IPC

A Rust function marked #[tauri::command] that the page can call by name through invoke('name', args), which crosses from the web view to the Rust process (inter-process communication) and returns a promise. It is an RPC; arguments and results are JSON, or raw bytes for a binary body.

Here ten commands, listed below.

Plugins, capabilities, CSP

Plugins add ready-made native features (dialogs, files, opening a URL). Capabilities are an allow-list: a window may call only the commands and plugin functions granted to it, with file scopes. The CSP (content security policy) tells the web view which origins the page may load scripts from or connect to. Together they play the role of a sandbox policy.

Here src-tauri/capabilities/default.json and the security.csp block of tauri.conf.json.

Security model, in one paragraph

The page may read and write only: files picked in a dialog (the dialog plugin adds each path to the fs scope), the two command-line folders (added by cli.rs), project files opened by the system (added by opened.rs), and $APPDATA/tiles and $APPDATA/projects. video.rs refuses to write a file that is not in the scope. The CSP restricts script to 'self' and lists every tile, weather, Overpass and Strava host the page may contact: a new data source must be added to img-src and/or connect-src there, or the desktop app silently blocks it while the website works.

  1. Open a file. « Ouvrir », a drop on the window, « Essayer avec l'exemple », or a Strava activity. openFiles in src/ui/projectActions.ts splits projects from tracks (routeOpenedFiles), then importTrackFiles → runImport builds one job per file.
  2. Parse. importFile (src/import/index.ts) picks parseGpx or, after a lazy import('./fit'), parseFit; buildTrack (import/stats.ts) computes statistics (distance, gain, duration, bounds); assignColors gives each track a colour. One failing file never stops the others (runImportJobs).
  3. Complete and store. importFiles (src/ui/importFlow.ts) fills missing elevations from the terrain source (completeImportedElevations) and calls useAppStore.addTracks, which recomputes bounds, fixes frameOrigin once (computeFrameOrigin), picks the regional imagery (IGN or swisstopo when the tracks lie inside their coverage: pickRegionalImagery) and bumps fitRequest.
  4. Build the scene. With a track present, FlyoverCanvas mounts TerrainLayer, which creates the terrain engine for the local frame; CameraRig fits the camera to the tracks on fitRequest. Each frame the engine selects tiles by screen-space error, fetches and decodes them, and builds meshes (terrain).
  5. Compute the film. useFilmClock() (src/scene/usePacing.ts) turns the track, the film, the flight duration, the pacing and the landmarks into a FilmClock (filmClockFor in src/film/clock.ts): a pure mapping from film time to phase (opening, flight, stop, closing) and progress. New films get automatic stops (film/assemble.ts).
  6. Play. FlyoverRig advances playback (setProgress(progress, timeS)), calls filmViewAt (which calls computeFilmView) and places the camera and the marker; OverlayCanvas redraws the overlay.
  7. Fetch side data. The panels call syncWeather (weather/store.ts) and syncLandmarks (osm/store.ts) from effects; the results are published in small stores that the sky, clouds, labels and overlay read. (This is why the side panels stay mounted: App.tsx notes their side effects.)
  8. Export. ExportPanel calls useExportStore.getState().start(request); ExportController (mounted in the canvas) runs runExport: frame schedule, then for each frame set progress and film time, renderSettledFrame (render until the visible tiles are final), composeFrame (WebGL image plus overlay into an OffscreenCanvas), session.addFrame; finally session.finish() and the file is closed.
  9. Save. serializeProject → encodeProjectFile (gzip with a signature) → getPlatform().saveDocument.

Import and geography

What. Turns a GPX or FIT file (or a Strava activity, or a planned route) into a Track, and converts between geographic, Earth-centred, local and tile coordinates. Key idea. A track is plain data, built once; everything downstream (path, camera, overlay, weather) derives from it and caches per track object.

  • GPX (import/gpx.ts, parseGpx): the browser's DOMParser, matching elements on localName so any extension vocabulary (Garmin, Cluetrust) works. A time without a time zone is read as UTC (a review fix).
  • FIT (import/fit.ts, parseFit): an in-house binary decoder written from the public FIT description; reads record, hr, session, sport and activity messages; positions are semicircles converted to degrees. Loaded only when the first .fit arrives (dynamic import).
  • Statistics (import/stats.ts): distance, bounds, duration; ascent and descent from smoothed elevations with a hysteresis threshold so GPS jitter does not count as climbing.
  • Missing elevation: terrain/elevation.ts reads heights from the terrain tiles (automatically at import for usual outings, otherwise « Calculer l'altitude »); Track.elevationEstimated remembers it.
  • Planned outing (plan/timing.ts): a route without times gets estimated ones from a date, a start time, an activity and a pace, so the sun, counters and weather work.
  • Strava (strava/): the user brings their own Strava application; client id and secret are kept in the platform storage and sent only to strava.com. Pure URL builders and parsers are tested; the rest calls fetch.
  • Chaining (import/chain.ts): several tracks merged into one route; after chaining, items placed on the old tracks are not moved (a known limit in how-it-works.html).
  • Geo (geo/): createLocalFrame, lonLatToEcef, tile maths (tilesForBounds, tileBounds, parentOf, childrenOf), geoid undulation (geoidUndulation, a 1° EGM96 grid generated into egm96Grid.ts by scripts/gen-geoid.mjs; edit the script, not the generated file).
Where to look src/import/, src/geo/, src/ui/importFlow.ts, src/ui/projectActions.ts. Tests: src/import/*.test.ts with fixtures in src/import/__fixtures__/ (a real Garmin run is read in a test), src/geo/*.test.ts. Design: Modules, Track chaining, Strava import.
How to modify To read a new file type, write parseX(...): Track[] that ends with buildTrack, add its extension to supportedExtension and the switch in importFile (import/index.ts), add it to the dialog filters in ui/projectActions.ts (chooseTracksToImport, chooseFilesToOpen), add a fixture and tests, and add the new Track['source'] value in core/types.ts if it is a new origin.

Terrain and imagery: fetch, cache, level of detail

What. Builds the 3D ground from open tiles: elevation tiles become a height grid, aerial photos become a texture, and a quadtree decides which tiles to show at which detail. Key idea. A tile is replaced by its four children only when its triangles would look bigger than about 3 pixels on screen (errorTargetPx); the parent stays until the children are ready, so the ground never flashes empty.

  • Sources (terrain/sources.ts): TERRAIN_SOURCES (Mapterhorn by default, AWS Terrain Tiles) and IMAGERY_SOURCES (ids: ign-ortho, swisstopo, arcgis-world-imagery, the hand-picked national photos basemap-at, gsi-photo and usgs-imagery, and the maps ign-plan, swisstopo-carte, opentopomap; terrain: mapterhorn, aws-terrarium). An id that was removed is mapped to a replacement in REMOVED_IMAGERY_SOURCES (project/document.ts). Every value was checked by hand; the log is docs/sources.md. This file is the single source of truth: buildTileUrl(source, key) builds URLs, sourceCovers tests coverage. The default imagery is Esri World Imagery; addTracks switches to IGN or swisstopo when the tracks fall inside their coverage, until the user picks one by hand.
  • Fetch (terrain/fetch.ts, createTileFetcher): fetch() then createImageBitmap(), a priority queue, 12 concurrent requests, de-duplication of requests in flight, an LRU cache of bitmaps (size from deviceBudget()), retries with growing delays (250 ms, ×4), abort support. Offline packs are read before the network through setStoredTileReader.
  • Heights (dem.ts): Terrarium encoding h = R*256 + G + B/256 − 32768; a pixel with alpha 0 or the all-zero sentinel is « no data ». heightField.ts answers sampleHeight(lon, lat) from the deepest loaded tile; the engine's own sampleHeight reads the tile actually drawn there, which is what the track draping and camera use.
  • Mesh (mesh.ts): a grid of 64 segments per tile edge (65 × 65 vertices) in the local frame, plus skirts (edges lowered) that hide cracks between detail levels.
  • Imagery (imagery.ts): for a terrain tile at zoom z the imagery sub-tiles at z + imageryZoomOffset are drawn into one canvas texture; the canvas is released once the GPU has it (phones cannot afford the memory) and redrawn after a WebGL context loss.
  • Engine (quadtree.ts decides what to draw and load; engine.ts owns loading, unloading, retries and the Three.js group). Dependencies are injected (EngineDeps) so tests run without network or GPU. In an export, setExporting(true) makes the engine retry failed tiles and report pendingVisibleTiles so the export can wait for a complete image.
  • Phones: core/deviceBudget.ts lowers caches, texture size and pixel ratio on touch devices; the level of detail holds a tile cap there (lodFactor).
Where to look src/terrain/, src/scene/TerrainLayer.tsx, terrainContext.ts, terrainLayerSetup.ts, src/core/deviceBudget.ts, vite.config.ts (TILE_PROXIES). Tests: src/terrain/*.test.ts (engine with fake downloads), src/scene/TerrainLayer.test.tsx. Design: Terrain engine, Device budget.
How to modify A new tile source: recipe. A different level-of-detail trade-off: errorTargetPx in the engine options and EngineTuning in engine.ts; re-measure on a phone, because the phone tile cap is tuned (the history has several fixes for white or flipping tiles).

Flyover camera and pacing

What. Decides where the camera is and where it looks, at every instant. Key idea. The view is a pure function of progress, film time, camera settings and a terrain height sampler: computeCameraView keeps no memory between frames, so the export can compute any frame on its own and the preview always matches it.

  • Path (flyover/path.ts): a track flattened into a polyline indexed by cumulative distance; samplePath(path, distanceM) maps progress to a position at constant ground speed. trackPathOf caches per track; smooth.ts averages GPS jitter (smoothedTrackPath), and the marker, camera and drawn line all use the same smoothed positions.
  • Camera (camera.ts, cameraSettings.ts): five styles (CAMERA_STYLES: chase, sway, orbit, top, cinematic), twelve presets (CAMERA_PRESETS), a minimum ground clearance, and a sight-line check against the relief. Time-based motions (orbit, cinematic swing) follow the film time so they keep moving while the progress is held. timeSmoothing.ts smooths in film time.
  • Film camera (filmCamera.ts, computeFilmView): wraps the flight camera with the opening and closing shots (SHOT_STYLES: aucune, descente, saut, situation, balayage), the camera of a stop (orbit, wide, fixed), camera keys, and the region view. With several tracks, follow.ts says what the camera follows.
  • Pacing (pacing.ts): only the film-time to progress mapping changes (raised-cosine slow-downs, pauses, speed portions); progress stays the fraction of distance. flightPacing(...) returns totalTime, progressAtTime, timeAtProgress. The default flight lasts 60 s, adjustable 15 to 600 s.
  • Sun, climbs, colours: sun.ts (the sun date under the marker: a dawn outing replays its sunrise), climbs.ts (detected climbs, categories 4 to HC), trackColor.ts (colour by speed, slope, elevation, heart rate…, with viridis and magma scales), nights.ts (multi-day tracks).
  • Several tracks: sequence.ts (« À la suite »: stages flown one after the other on a never-stored sequence track), race.ts (« En parallèle »: ghost race and leaderboard).
Where to look src/flyover/, src/scene/FlyoverRig.tsx (applies the view), src/scene/filmView.ts. Tests: src/flyover/*.test.ts including continuity checks (__fixtures__/smoothness.ts). Design: Flyover.
How to modify New camera style: add it to CAMERA_STYLES and CAMERA_STYLE_LABELS in cameraSettings.ts (i18n key camera.style.<id> in the camera.ts of each language), handle it where camera.ts switches on the style, make it a function of film time only, add it to the continuity test. Weather and OpenStreetMap data

  • Weather (weather/openMeteo.ts): a few places sampled along the track, the hourly values of its days fetched in one request to the Open-Meteo archive (past outing) or forecast (up to 16 days ahead, FORECAST_DAYS), cached per place and UTC day (archive days in memory and storage, forecast for 3 hours). A refusal (HTTP 429) becomes a message that names the quota used up, minute, hour or day (tooManyMessage); the later stages of « À la suite » are fetched one at a time (syncStageWeather), and a failed one is reported in the weather panel with a « Réessayer » button. series.ts is the data model with interpolation in time and place; sceneWeather.ts turns it into scene parameters (dimmed sun, haze, veiled sky, exposure) and sceneClouds.ts into cloud layers (the cloud cover is read at up to 12 places, about one every 10 km, so the sky changes along the track; the clouds also cast shadows on the terrain, setting cloudShadows, scene/cloudShaders.ts). Both are pure functions of (data, instant, place, setting), so the export renders the same weather for the same frame. weather/store.ts holds the result; syncWeather is idempotent so effects may call it freely.
  • Landmarks (osm/overpass.ts): one bounded Overpass query per track (a plain bounding box is far cheaper than around: on a polyline), one request at a time, one retry then the next endpoint, form-encoded POST so the browser sends a « simple » CORS request, cached for 30 days (CACHE_TTL_MS). Distance to the track is computed locally in landmarks.ts, so changing the kinds or the distance never sends a new request. Each landmark is « Auto », « Toujours » or « Jamais » shown (landmarkMode, withMode); the density (few, normal, many) caps the Auto ones; « Garder les Toujours » dismisses the others until « Relancer la recherche » (dismissedIds); ui/LandmarkMap.tsx is the window with the map and the elevation profile to pick them. osm/water.ts (lakes and rivers for the water layer) and osm/region.ts (the administrative region highlighted by the « situation » shot) use the same client.
  • Privacy and terms: services receive only the tile area, a few points rounded to 1 km for the weather, and the box around the track for landmarks; Open-Meteo is for non-commercial use, Esri tiles follow Esri’s terms (README.md « Data sources »).

The export pipeline

What. Produces an MP4 or WebM video (16:9, 9:16, 1:1, 4:5, 21:9, 720p to 4K, 24, 30 or 60 fps), a PNG or JPEG still, the overlay alone on a transparent background, several formats in one go, one film per track of a folder, and the poster. Key idea. The export never plays in real time: it walks a list of frames, and each frame waits until its terrain is final, so a slow computer gives the same film, only later.

  1. ExportPanel builds an ExportRequest and calls useExportStore.getState().start(request) (phase starting). The destination file is chosen from the click that starts it (chooseVideoDestination), so the website's file picker still has the user gesture.
  2. ExportController, mounted inside the canvas, sees the request and runs runExport: buildFrameSchedule gives the progress of each frame, buildFrameTimes its film time (one extra second held at the start, two at the end). Playback is paused, frameloop is set to 'never', the renderer is resized to the video size at pixel ratio 1.
  3. For each frame: filmClock.stateAt(time); the motion-blur sub-frames (shutterSamples); renderSettledFrame renders until the engine reports no pending visible tile (up to 5 minutes per frame, then the export stops with the tile named: tileFailureMessage); composeFrame draws the WebGL canvas and the overlay into an OffscreenCanvas.
  4. session.addFrame(i) hands the frame to the encoder (createVideoEncoder: WebCodecs through mediabunny; or createNativeVideoEncoder: Rust and ffmpeg). Encoding overlaps the render of the next frame. Held frames (stops, holds) reuse the previous image when nothing moves with time.
  5. session.finish() closes the file (streamed to disk when the platform allows, else built in memory and downloaded). Everything is restored on success, error or cancel. State goes rendering → finalizing → done | error | canceled in export/store.ts; ended renders are kept in a history (history.ts, historyStore.ts).
  • Quality tiers (qualityTier.ts): « Standard / Haute / Maximale » set the bitrate (QUALITY_BITS_PER_PIXEL in encoder.ts, a codec factor, a device cap) and how much the costly effects are computed at export time only; the project is never rewritten.
  • Batch (batch.ts, trackFilms.ts): « Plusieurs formats » and « Un film par trace » run jobs one after another through the same store. cliRender.ts does the same from the desktop command line.
  • Phone safety (guard.ts): screen kept on, a flag in sessionStorage to report an export the browser killed, breadcrumbs of the steps; diagnostic.ts builds a report kept in French on purpose (withLanguage('fr', …)) because it is pasted into bug reports.
  • Poster (src/poster/): a pure layout (layout.ts: boxes in pixels from the size, style and rows present; text fitting) and a drawing function (draw.ts), fed by export.ts with a 3D still.
Where to look src/export/ (start with ExportController.tsx and capture.ts), src/ui/ExportPanel.tsx, src/poster/, src-tauri/src/video.rs. Tests: src/export/*.test.ts (encoder and network faked), e2e scenarios « export » and « historique » (render a real 320 × 180 film). Design: Video export, Export quality tiers, Poster.

Project persistence and migration

What. One self-contained file holding every setting, the tracks and the media. Key idea. Settings are handled generically over the keys of DEFAULT_SETTINGS: a new setting is saved, validated and restored without editing the persistence code.

  • Document (project/document.ts): PROJECT_FORMAT = 'openflyover-project', PROJECT_VERSION = 2; serializeProject(state, name, media) writes tracks column by column (lon, lat, ele, time…, with a fixed number of decimals) and settings as they are; parseProject(text) returns a LoadedProject with warnings.
  • Validation: sanitizeSettings(raw, base) takes each key of DEFAULT_SETTINGS from the file when it has the same shape as the default (sameShape) and passes its extra check in SETTING_CHECKS (enums, catalogue ids, ranges); otherwise the default is used and the key is listed as invalid (a warning, never a failure). SETTING_UPGRADES fills in fields added since a project was saved (withCameraDefaults, withOverlayDefaults…), so old files and presets keep loading.
  • Migrations: MIGRATIONS[n] upgrades a document from version n to n + 1; migrateProject runs the chain and refuses a newer version. Today there is one migration (1 to 2).
  • File container (project/file.ts): .opnflvr is an 8-byte header (the ASCII signature OPNFLVR and a version byte: 1 gzip, 2 plain) followed by the JSON text, gzip-compressed with the browser's CompressionStream. Older .json projects have no signature and are read as they are.
  • Apply (project/apply.ts): applyProject replaces tracks, settings, media and playback speed, then fits the camera. Opening is refused during an export.
  • Undo (project/history.ts): createHistory watches immutable settings snapshots, keeps for each step only the keys that changed, merges changes to the same keys within 400 ms (COALESCE_MS, a slider drag) and keeps 100 steps. transaction(fn) groups several changes (a preset); beginGesture keeps one step open.
  • Presets (project/presets.ts): named sets of settings in the key openflyover.presets.v1, by scope (PRESET_SCOPES: tout, carte, trace, habillage, prise-de-vue).
  • « Mes projets » (platform/projectLibrary.ts): projects kept inside the app (Cache Storage on the web, files on the desktop), saved automatically (installLibraryAutosave in ui/library.ts).

State management, summarised

See the mental-model part for the idea. In practice: project data goes in useAppStore (so it is saved and undone), transient data in a small store beside the module that owns it, and preferences of the device (theme, language, layout) in usePreferences and getPlatform().storage. Pure modules never import a store; components and hooks do. Components select the smallest value they need. Anything a frame needs from the store inside useFrame is read with useAppStore.getState() rather than a hook, so a store change does not re-render React.

How to modify A new non-project store: create<State>()(…) in its module, an install… function if it needs start-up wiring (called from main.tsx), and a reset in tests (useX.setState(initial) in beforeEach). If its changes should wake the 3D view, add it to the subscriptions in renderOnDemand.ts.

Unit tests (Vitest)

A unit test calls one module with known inputs and checks the output; Vitest is the runner (like JUnit or pytest), configured in the test block of vite.config.ts.

  • Where: src/**/*.test.ts and *.test.tsx, next to the module they test, but not always under its name: the tests of scene/trackLineSet.ts are in TrackLines.test.tsx, those of overlay/themes.ts in overlay/settings.test.ts. Search with grep -rln functionName src --include='*.test.*'. Fixtures: __fixtures__/ folders.
  • Environment: node by default. A file that needs the DOM (a component, DOMParser, canvas) starts with // @vitest-environment jsdom (jsdom is a simulated browser). CSS is stubbed out in tests, except fonts.css.
  • Pool: one isolated worker thread per file (pool: 'threads'), about 6 s faster than forked processes according to the comment in the config.
  • Language: tests run in French (installLanguage() is only called from main.tsx), so they assert the French texts.
  • How things are isolated: pure modules take plain values; the terrain engine takes its dependencies as an argument (EngineDeps); network and the video encoder are faked; invoke of Tauri is an injectable parameter; stores are reset in beforeEach (resetAppStore()).
  • Run one file or one test: npx vitest run src/film/clock.test.ts, npx vitest run -t "pickRegionalImagery", or npx vitest for watch mode.
  • What is not tested automatically: how the 3D rendering looks, sound, export speed on a real GPU, and (per how-it-works.html) interface components beyond the ones with a .test.tsx; the manual list is Manual checks on a real machine.
Reading a failing test
  1. Read the first FAIL block, not the last: the file, the test title, then the diff (- Expected / + Received) and the line of the failing expect.
  2. Run only that file (command above) until it passes, then the whole suite.
  3. A TypeScript error shown by Vitest is not type checking (Vitest strips types): run npm run typecheck for those.
  4. If a test passes alone and fails in the suite, look for state kept in a module-level store or variable that the test did not reset.
  5. A timing failure under load: the suite runs files in parallel threads; retry with --maxWorkers=1. The history has fixes that gave slow tests explicit timeouts (3a7e98c).
  6. Do not « fix » a test by loosening it before you know whether the code or the test is wrong. Tests such as the clock continuity and « export equals preview » checks exist to catch exactly the mistakes this architecture invites.

Debugging and performance

  • Browser developer tools (F12 in Chrome or Edge): Console shows errors and the app's own logs ([export] lines during an export: render time breakdown, tile waits, encoder wait); Network shows tile, weather and Overpass requests (look for 4xx and 5xx, and for a missing Access-Control-Allow-Origin); Sources shows your TypeScript through source maps in development; Application shows localStorage (keys starting with openflyover.), Cache Storage and the service worker (use « Update on reload » or « Unregister » when testing it); Performance records a trace.
  • In the app: « Réglages » has a « Diagnostic » section: « Afficher le rapport » opens the « Rapport de diagnostic » (device, GPU, settings, no track names; kept in French on purpose) and a test export without encoding; the status bar shows fetch states and, on the desktop, memory and CPU; the export history lists the time and a summary of the settings of past renders (export/history.ts).
  • Blank or white terrain: Network tab. A tile request failing, or an imagery source answering white tiles outside its coverage (the engine detects and replaces them), or CORS. Try another imagery source.
  • The 3D view does not update: the scene renders on demand. If a new store should trigger a redraw, check renderOnDemand.ts (wakeScene, sceneChanged); a hand-made change of a three.js object may need invalidate() from @react-three/fiber.
  • Slow preview: lower the cloud quality and the lens effects (the « poids de rendu » pictograms rank settings by cost, ui/renderCost.ts); check the pixel ratio (deviceBudget()); record a Performance trace and look at useFrame callbacks.
  • Export problems: read the message (it names the tile and the server), the [export] console lines and the diagnostic report; on a phone the tab may be killed for memory (export/guard.ts reports it at the next start).
  • Production-only bugs (service worker, base path, chunk loading): npm run build && npm run preview; for a sub-path deploy, build with BASE_PATH=/x/.
  • Desktop-only bugs: npm run tauri:dev, and run cargo test --locked in src-tauri/. Remember a missing host in the CSP or a missing capability fails silently or with a console error in the web view.

From an issue to a pull request

The open issues of the repository carry « Leads to investigate » and « More help — step by step » comments built on one method. It works for any bug or small feature.

  1. Reproduce, and write down what you see before reading code: the exact steps, a screenshot, the style or preset used. Play the film twice: a problem seen only on the first playback comes from tiles still loading (level of detail); one that stays is in the logic.
  2. Find the chain from what you see to the pure function behind it: a French label, its key in src/i18n/fr/, the component in src/ui/, the setting in src/state/store.ts, the module that computes (Where do I find …). Components only wire things together; the decision is almost always in a pure .ts function.
  3. Find its tests (not always under the module's name) and run them alone: npx vitest run path/to/file.test.ts. They tell you what the function promises today.
  4. Measure before changing: a throwaway test file that calls the function with your case and prints the values (console.log, console.table; add --silent=false if nothing shows), or a temporary log in the running app. Do not commit it. The numbers choose your thresholds and prove the fix afterwards.
  5. Write the failing test, then the change, within the repository's rules: no state between frames, a new Track field is optional and handled by both halves of project/document.ts, a new setting follows the recipe.
  6. Check every consumer: search the function and the pattern it relies on (for heights, ?? at.ele); npm run typecheck lists every Record and language file that misses a new id.
  7. Close the loop: npx vitest run, npm run typecheck, npm run lint, the manual check of the first step, then the docs (CHANGELOG.md if visible, ARCHITECTURE.md if a contract or a documented value changes). If an issue comment pointed to the wrong place, say so in the issue.

Add a setting, end to end

Example: a new on/off or numeric option of the project. Because settings are handled generically, persistence and undo come almost free.

  1. Type and default in src/state/store.ts: add the field to interface Settings (with a one-line comment) and to DEFAULT_SETTINGS. If the setting is a structured object, define its type, DEFAULT_X, isValidX and withXDefaults in the module that owns the concept (as scene/lens.ts does for lens) and import them into the store.
  2. Validation in src/project/document.ts: nothing is needed for a boolean or a free number (the shape is checked against the default). Add an entry to SETTING_CHECKS when a value of the right type can still be invalid (an enum, a catalogue id, a range). If you add fields to an existing object setting, add or extend its entry in SETTING_UPGRADES so older projects and presets still load. Note that an empty array default accepts any array.
  3. Behaviour: read it where it acts. In the 3D scene, a component under src/scene/ selects it (useAppStore((s) => s.settings.x)); the view wakes on its own, because renderOnDemand.ts reacts to any change of the app store. In a pure module, pass it as a parameter (never import the store). The export reads useAppStore.getState().settings at run time, so check that nothing you added is captured before the export starts.
  4. Control in the panel of the right tab (see the table in the next recipe): inside a PanelSection title=… keys={[…, 'x']} (the keys drive the « modifié » marker and the per-section reset to defaults), a SettingRow label value paths={['x']} for a secondary setting, or a primitive (Switch, Checkbox, Select, NumberField, RangeField for a slider). Write with setSetting('x', value). Copy the nearest existing row.
  5. Texts: add the label, hint and any tooltip to src/i18n/fr/<domain>.ts then to the same file of each other language, and use t('domain.key') from useT(). See the i18n recipe.
  6. Presets (optional): to include it in a preset family, add the key to PRESET_SCOPE_KEYS in src/project/presets.ts.
  7. Export cost (optional): if it lengthens the export, give its row a weight and add it to src/ui/renderCost.ts.
  8. Tests: the default and any pure logic next to the module (store.test.ts for the store); a round trip in src/project/document.test.ts (saved, loaded, an invalid value falls back to the default with a warning, a project without the key loads); a component test only if the control has logic. The i18n parity test runs by itself.
  9. Docs: a line in CHANGELOG.md if visible; docs/user-guide.html (French) if users need to know; ARCHITECTURE.md if it is a contract.
Verify
  • Change it, undo (Ctrl+Z), redo: one step per drag.
  • The panel shows « modifié » and the reset puts back the default.
  • Save, reload, open the project: the value is back. Open an older project (or a file without the key): no error, default value.
  • The export looks like the preview. Switch to English: no missing text.

No migration is needed to add a key: a missing key takes its default. Raise PROJECT_VERSION only if you change the meaning of existing data in a way SETTING_UPGRADES cannot express.

Add a keyframed setting

Example: let a film-wide setting vary along the track with keys (like the exposure, the sun hour, the grading or the 3D-label opacity). The keys are generic, you only declare the setting.

  1. src/film/paramKeys.ts: add the name to FILM_PARAMS and an entry to PARAM_SPECS (label through t(), min, max, step, format; log for a factor), to PARAM_LANE_LABELS and to paramBase (the value the setting has without a key, read from the settings). film/model.ts validates the keys against FILM_PARAMS, so nothing else changes there; the timeline lane, the undo and the project file follow.

Glossary

Web, 3D and Rust terms in the sense they have here, then the project's own vocabulary, including the French words of the interface (the French text is the reference; the English interface follows the terminology table of ARCHITECTURE.md).

Web and tooling

Bundler

Tool that merges many source modules into few optimised files and splits rarely used code into on-demand chunks. Here: Vite (Rolldown).

Chunk

One output file of the bundler, loaded on demand through import().

DOM

The tree of elements of the page that the browser draws. React updates it for you.

ES module

JavaScript's native module system (import / export); the whole code base uses it.

HMR

Hot module replacement: the dev server swaps a changed module in the running page without a reload.

Lock file

package-lock.json, Cargo.lock: exact versions of every dependency, committed.

Lint

Static analysis for risky or inconsistent code. Here oxlint.

jsdom

A simulated browser in Node, used by tests that need a DOM.

Promise / async

A value that arrives later (a future); await pauses the function until it does, without blocking the page.

Service worker

A script that sits between page and network and can answer from a cache. Website only: platform/serviceWorker.js.

Static site

A folder of files served as they are; all logic runs in the visitor's browser.

Cache Storage

Browser store of responses keyed by URL; here the offline tiles and « Mes projets ».

CORS

The browser rule that a page may read a response from another site only if that site allows it with a header. Every tile source must send it.

CSP

Content security policy: the list of origins a page may load from or contact. Set for the desktop app in tauri.conf.json.

React and interface

Component

A function that returns a piece of interface from its props and state.

Props

The inputs of a component, like function arguments.

State

Data that, when changed, makes the interface redraw. Local (useState) or shared (a store).

Hook

A function named use… that gives a component memory or lifecycle. Called unconditionally.

Effect

useEffect: code run after render, with a cleanup, to talk to the outside world.

JSX / TSX

HTML-like notation inside JavaScript / TypeScript; the file extension is .tsx.

Selector

A function that picks a value out of a store; the component re-renders only when that value changes.

Store (zustand)

A shared observable state object with actions: useAppStore and about twenty smaller ones.

Suspense / lazy

On-demand loading of a component with a placeholder while it loads.

StrictMode

A development mode that runs effects twice to expose leaks.

Primitive

The project's wrapper of a HeroUI component, in src/ui/primitives/.

Token

A named design value (colour, radius, spacing) in theme.css.

Utility class

A single-purpose Tailwind class (gap-2); @utility names a repeated combination.

React Aria

Adobe's headless components for keyboard, focus and screen-reader behaviour, under HeroUI.

3D, video and sound

WebGL

The browser's API to the graphics card.

Shader

A small program that runs on the GPU per vertex or pixel.

Mesh

A surface made of triangles; a terrain tile is a 65 × 65 vertex grid plus skirts.

Texture

An image painted on a mesh; here the composed aerial photo of a tile.

Scene graph

The tree of objects three.js renders.

Render loop

The per-frame cycle: update, draw. Here on demand (frameloop="demand").

Post-processing

Image effects applied after the scene is drawn (haze, tone mapping, grading, bloom).

LOD

Level of detail: finer tiles near the camera, coarser far away. Here a quadtree.

DEM

Digital elevation model; here elevation tiles decoded from colours (Terrarium).

Tile (XYZ)

A square map image addressed by zoom z, column x, row y; y = 0 at the north.

Draping

Laying the track line on the ground: each point takes the terrain height under it, or its recorded elevation where no terrain is loaded, times the exaggeration, plus a 3 m lift (computeDrapedPositions).

Skirt

Edge of a tile lowered below the ground to hide cracks between detail levels.

ECEF / local frame

Earth-centred coordinates; the local tangent frame the scene uses (X east, Y up, Z south).

Geoid / MSL

Mean sea level surface; heights are above it (geo/geoid.ts).

Canvas 2D / OffscreenCanvas

A drawing bitmap with 2D commands; the overlay and the poster are drawn on one.

Frame / fps

One image of the film / images per second (24, 30, 60).

Codec / container

The compression of video or sound (H.264, VP9, AAC, Opus) / the file format that holds the streams (MP4, WebM).

WebCodecs

Browser API to the system's encoders. mediabunny writes the container.

ffmpeg

A command-line video tool; used by the Linux desktop app where WebCodecs is missing.

SwiftShader

Software GPU used by headless Chromium in tests: correct, slow.

Rust and Tauri

Crate

A Rust package, library or program.

Cargo

Rust's build tool and package manager (Cargo.toml, Cargo.lock, cargo test).

Tauri

Framework showing a web site in a native window with a small Rust backend.

Web view

The operating system's own browser engine inside the window (WebView2, WebKit, WebKitGTK).

Command

A Rust function the page can call with invoke (#[tauri::command]).

Plugin

Packaged native feature: dialog, fs, oauth, opener, and for updates updater and process.

Capability / permission

The allow-list of what the window may call; capabilities/default.json.

IPC

Inter-process communication between the web view and the Rust process.

fs scope

The set of paths the page may read or write; grown by dialogs and by cli.rs / opened.rs.

Tiles of a corridor along the track kept for use without a connection.

Projects kept inside the app, with thumbnails.

What the repository does not say

These are gaps found while writing this handbook. They are not guesses made into facts: if you learn the answer, write it where the decision lives.

  • Why Tauri was chosen over another desktop shell (the code shows how it is used, not the comparison).
  • Why no Web Worker is used, and whether heavy work (mesh building, DEM decoding) was ever measured on the main thread.
  • Whether the macOS and Linux desktop builds run correctly: the documents say they have only been built by CI.
  • Some figures in older documents (test counts, number of e2e scenarios, number of camera presets, number of Tauri commands) differ from the code today; this page counts from the code.
